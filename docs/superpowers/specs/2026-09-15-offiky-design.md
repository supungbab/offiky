# offiky 설계

작성일: 2026-09-15
대상 플랫폼: macOS 26.0 이상, App Sandbox 활성화

## 1. 목적

같은 사내 네트워크를 사용하는 맥 사용자들이 각자의 데스크톱 위에 16×16 픽셀 캐릭터로
존재를 표현하고, 전역 단축키로 한 줄 메시지를 주고받는 상주 앱이다.

핵심 가치는 두 가지다.

- 동료가 지금 자리에 있다는 감각을 작업 화면을 벗어나지 않고 얻는다.
- 말을 걸기 위해 다른 앱으로 전환하지 않는다.

## 2. 확정된 범위

| 항목 | 결정 |
|---|---|
| 좌표 공유 | 가로 위치 `x` 와 높이 `y` 모두 포인트 절대값. 원점은 띠의 왼쪽 끝이며 양 끝은 각자의 데스크톱 폭이다. 화면이 좁으면 멀리 있는 동료가 보이지 않는다. |
| 채팅 | 전역 단축키로 입력줄 표시 + 말풍선 5초. 대화를 보관하지 않는다. |
| 캐릭터 움직임 | 바닥 전체를 자유롭게 돌아다니고 가끔 점프하거나 대시한다. 빠르게 정면 충돌하면 피격한다. 드래그로 들어 올릴 수 있고 놓으면 떨어진다. |
| 참가 제한 | 없다. 같은 네트워크에서 앱을 실행하면 자동으로 참가한다. 전송은 평문이다. |
| 규모 | 동시 접속 50명 이상을 상정한다. |
| 전송 구조 | 서버 없이 Bonjour 로 발견하고 자동 선출된 호스트가 중계한다. |
| 표시 인원 | 접속자 전원을 표시한다. |
| 캐릭터 | 내장 9종 중 하나를 골라 색을 조정한다. 스프라이트 시트를 2배로 표시하며 대기·걷기·피격·점프·대시 5동작을 재생한다. |

## 3. 앱 구조

`LSUIElement = true` 로 Dock 아이콘을 제거하고 `MenuBarExtra` 로 메뉴바에만 상주한다.

Xcode 템플릿이 생성한 `Item.swift`, `ContentView.swift`, SwiftData 관련 코드는 사용처가
없으므로 삭제한다.

메뉴바 메뉴 구성:

- 채팅 열기
- 내 캐릭터 편집…
- 캐릭터 숨기기 (토글) — 내 화면의 표시만 중단한다. 접속과 좌표·채팅 전파는 유지되므로
  동료 화면에서는 내 캐릭터가 그대로 보인다
- 내 이름 변경…
- 종료

### 3.1 오버레이 윈도우

캐릭터 하나에 윈도우 하나를 배정하면 50명 규모에서 WindowServer 부담이 커진다.
**디스플레이마다 오버레이 윈도우 1개**를 배치하고 그 안의 SpriteKit 씬 하나가 해당 화면의
캐릭터 전부를 렌더링한다. 윈도우 개수는 모니터 개수와 같다.

윈도우 설정:

- `styleMask: .borderless`
- `isOpaque = false`, `backgroundColor = .clear`, `hasShadow = false`
- `level = .floating`
- `collectionBehavior = [.canJoinAllSpaces, .stationary, .fullScreenAuxiliary]`
- `frame = screen.visibleFrame` — 메뉴바와 Dock 이 차지한 영역을 제외한다

씬 설정:

- `preferredFramesPerSecond = 30` — 애니메이션 재생 속도의 상한이 된다. 12fps 로 두면
  걷기·대시가 아무리 빨라도 초당 12장을 넘지 못한다. 24fps 에서는 대시(18fps)가 고르게
  샘플링되지 않아 어떤 장은 두 번, 어떤 장은 한 번 나온다. 점프는 0.6초라 15장뿐이라
  한 장만 밀려도 공중에서 멈춘 것처럼 보인다

**드래그 핸들 윈도우는 12Hz 로만 옮긴다.** 창을 옮길 때마다 윈도우 서버와 왕복이 생겨,
매 프레임 부르면 그것만으로 CPU 의 3할을 쓴다. 핸들은 클릭만 받으면 되므로 캐릭터를
정확히 따라갈 필요가 없다 — 12Hz 면 가장 빠른 대시에서도 7.5포인트 뒤처지는데 핸들이
40포인트라 덮고 남는다. 드래그 중에는 눌린 창이 커서를 계속 따라가므로 끊기지 않는다.

측정값이다 (Release, 화면 2개):

| | CPU |
|---|---|
| 60fps, 핸들 매 프레임 | 8.7% |
| 창을 바닥 240pt 만 덮게 | 8.2% |
| 60fps, 핸들 12Hz | 5.4% |
| **30fps, 핸들 12Hz** | **3.3%** |

**창 면적은 거의 영향이 없다.** 전체 화면 합성은 GPU 가 맡고 CPU 를 쓰지 않는다. 그래서
오버레이를 바닥만 덮게 줄이는 방안은 접었다 — 0.5%p 를 얻자고 드래그 높이를 제한할 값이
없다. 비용은 **프레임마다 반복되는 일의 개수**에 걸리지 그리는 면적에 걸리지 않는다.

**갱신은 `SKScene.update` 에서 한다. 별도 타이머를 두지 않는다.** 타이머와 렌더 루프는
서로 다른 시계라 위상이 어긋난다. 한 렌더 프레임에 갱신이 두 번 들어가거나 한 번도 안
들어가서, 같은 그림을 두 번 그리거나 두 칸씩 건너뛴다. 24Hz 타이머와 24Hz 렌더처럼 주기가
같으면 어긋남이 느리게 왕복해 몇 초에 한 번씩 끊겨 보인다.

화면마다 씬이 있으므로 `tick` 은 한 프레임에 여러 번 불린다. 경과 시간을 실측해서 쓰고
경과가 0 이면 건너뛴다. 갱신 주기가 조금 촘촘해질 뿐 결과는 같다.
- `SKTexture.filteringMode = .nearest` — 픽셀 경계가 흐려지지 않는다
- **표시 위치를 2포인트 격자에 맞춘다.** 픽셀 한 칸이 2포인트인데 소수점 위치에 그리면
  프레임마다 어떤 픽셀은 1포인트, 어떤 픽셀은 3포인트가 되어 몸이 일렁인다. 산책은 프레임당
  0.83포인트씩 움직이므로 거의 매 프레임 어긋난다. 물리 좌표는 소수점 그대로 두고 그릴 때만
  반올림한다

**자체 서명 인증서로 배포한다.** Apple 의 Developer ID 를 쓰지 않는다 — 개발자 프로그램을
갱신하지 않아도 계속 배포할 수 있어야 한다. 대가로 Gatekeeper 를 통과하지 못하므로 받는
사람이 격리 속성을 지워야 하는데, Homebrew 로 설치하면 cask 가 대신 처리한다.

애드혹 서명으로도 되지만 **빌드마다 신원이 바뀐다.** 그러면 macOS 가 로컬 네트워크 권한을
업데이트마다 다시 물어본다. 고정된 인증서가 그것을 막는다. `scripts/make_cert.sh` 가
한 번 만들어 둔다. 신뢰되지 않은 인증서라 `find-identity -v` 목록에는 안 보이지만 서명에는
쓸 수 있다.

**Hardened Runtime 은 유지한다.** 샌드박스가 앱이 바깥에 손대는 것을 막는다면, 이것은
바깥이 앱 안에 손대는 것을 막는다 — 코드 인젝션, 서명 안 된 라이브러리 로드, 다른
프로세스의 디버거 부착. 공증과 무관하게 값어치가 있고 켜는 비용이 없다.

**권한은 `offiky.entitlements` 파일로 명시한다.** 빌드 설정만으로 두면 배포 빌드에서
권한이 통째로 사라진다 — 공증에 필요한 `CODE_SIGN_INJECT_BASE_ENTITLEMENTS=NO` 가
`get-task-allow` 뿐 아니라 Xcode 가 생성한 샌드박스·네트워크 권한까지 지운다.
1.0.0 과 1.0.1 이 권한 없이 배포됐다. 파일은 동기화 그룹 밖(저장소 루트)에 둔다 —
`offiky/` 안에 두면 번들에 리소스로 복사된다.

**앱 샌드박스와 Hardened Runtime 을 모두 유지한다.** LAN 에 포트를 열고 아무나 보낸
데이터를 파싱하는 앱이라 격리가 값어치를 한다. 샌드박스가 없으면 `~/.ssh` 와
`~/.config/gh/hosts.yml` 이 이 프로세스에 그대로 열린다 — TCC 는 문서·데스크톱만 막는다.

업데이트를 앱에서 바로 설치하려고 잠시 껐다가 되돌렸다. **외부 프로그램 실행은 권한을
받을 수 있는 종류가 아니다.** 네트워크에는 `com.apple.security.network.client` 같은
엔타이틀먼트가 있지만 실행에는 그런 것이 없고, 사용자가 허락해 줄 대화상자도 없다.
자식 프로세스가 샌드박스를 물려받으므로 `brew` 를 띄워도 `/opt/homebrew` 와
`/Applications` 에 쓰지 못한다. 비샌드박스 헬퍼를 따로 설치하는 길은 있으나 헬퍼가
같은 구멍을 다시 만든다.

그래서 명령을 클립보드에 넣어 주는 선까지 한다. 얻는 것이 "붙여넣기 한 번 덜 하기" 인데
잃는 것이 격리라 교환비가 맞지 않는다.

### 업데이트 확인

실행할 때와 6시간마다 GitHub 릴리스 API 로 최신 태그를 조회한다. 인증 없이 시간당
60회가 한도라 30분 안에 다시 묻지 않는다.

- **버전 비교는 숫자로 한다.** 문자열로 비교하면 `2.0.10` 이 `2.0.9` 보다 낮게 나온다
- **응답의 주소는 `https` 와 `github.com` 인지 확인한 뒤에만 브라우저로 넘긴다.**
  원격 응답을 그대로 여는 경로라 스킴이 바뀌어 들어올 수 있다
- 새 버전이 있으면 `brew upgrade --cask offiky` 를 클립보드에 넣어 주거나 릴리스 페이지를
  연다. 둘 다 샌드박스 안에서 가능하다
- **메뉴에는 항목을 하나만 둔다.** 평소에는 "업데이트 확인…", 새 버전이 잡히면
  "새 버전 x 받기…" 로 이름만 바뀐다. 받는 방법은 대화상자에서 고르게 한다 —
  메뉴에 선택지를 늘어놓으면 평소에도 자리를 차지한다
- **직접 확인하면 결과를 대화상자로 알린다.** 메뉴는 누르는 순간 닫혀서 결과를 그 자리에
  붙일 수 없다. 최신·새 버전·확인 실패 세 가지를 모두 알린다 — 특히 실패를 조용히 넘기면
  사내망에서 GitHub 이 막혀 있어도 사용자는 최신인 줄 알게 된다

**오버레이 윈도우는 `ignoresMouseEvents = true` 로 지정한다.** 전체 화면 투명 오버레이는
투명한 영역의 클릭까지 전부 가로챈다. 표시 전용으로 두지 않으면 맥을 사용할 수 없다.

드래그는 **내 캐릭터를 따라다니는 32×32 포인트 윈도우 하나**가 받는다. 동료 캐릭터는 원래
클릭을 받지 않으므로 추가되는 윈도우는 1개다.

`NSApplication.didChangeScreenParametersNotification` 을 관찰한다. 모니터를 연결·해제하거나
배치·해상도를 변경하면 오버레이 윈도우 집합을 재구성하고 모든 캐릭터를 다시 배치한다.

`NSWorkspace.willSleepNotification` 에서 연결·리스너·브라우저를 정리하고,
`didWakeNotification` 에서 전부 재시작한다.

## 4. 캐릭터와 스프라이트

### 4.1 캐릭터 구성

캐릭터는 **내장 9종 중 하나에 색 조정값을 더한 것**이다. 픽셀을 직접 그리지 않는다.

```swift
struct Look: Codable {
    var design: Int        // 0~8
    var hue: Double        // -0.5 ~ 0.5  색상 회전
    var saturation: Double // 0 ~ 2       채도 배율
    var brightness: Double // 0.5 ~ 1.5   밝기 배율
}
```

그림을 전송하지 않고 **숫자 네 개만 전송한다.**

색 조정은 **픽셀 전체에 같은 HSB 변환을 적용한다.** 색마다 따로 고르게 하면 명암 관계가
깨져 그림이 뭉개진다. 색상은 더하고 채도·밝기는 곱한다.

### 4.2 스프라이트 시트

캐릭터마다 PNG 한 장을 `Assets.xcassets/characters` 에 둔다. 시트는 **가로 6프레임 ×
세로 5동작**이고 프레임 크기는 캐릭터마다 다르다(15×18 ~ 22×20 픽셀).

| 행 | 동작 | 프레임 | 재생 |
|---|---|---|---|
| 0 | 대기 | 4 | 5fps |
| 1 | 걷기 | 6 | 12fps |
| 2 | 피격 | 4 | 14fps |
| 3 | 점프 | 3 | 11fps |
| 4 | 대시 | 6 | 18fps |

프레임을 소스에 문자로 적지 않는 이유는 크기 때문이다. 9종 × 23프레임을 픽셀당 여섯 자로
적으면 소스가 100KB 를 넘는다.

실행 시점에 PNG 를 픽셀 배열로 읽어 색을 입히고 프레임마다 `SKTexture` 를 만든다.
`filteringMode = .nearest` 로 픽셀 경계를 유지한다. 결과는 `Look` 별로 캐시한다.

**걷기 반동은 스프라이트에 들어 있다.** 프레임마다 머리 높이가 1픽셀씩 오르내리도록 원화에
그려져 있으므로 코드에서 위아래로 흔들지 않는다. 둘을 겹치면 주기가 어긋나 불규칙하게 튄다.

**모든 동작의 발 높이를 맞춘다.** 시트를 만들 때 다섯 동작 전체의 경계 상자로 잘라내므로
프레임이 바뀔 때 캐릭터가 위아래로 튀지 않는다. 대시 자세가 가로로 밀려 있는 것은 원본의
의도이며 그대로 보존된다.

### 4.3 행동과 동작 전환

**대시 방향은 시작할 때 정하고 끝날 때까지 바꾸지 않는다.** 매 프레임 목표와 비교해 방향을
정하면 두 가지가 어긋난다. 벽에 막히면 목표가 벽 너머라 대시가 끝나지 않고, 목표를 지나치면
방향이 뒤집혀 되돌아온다.

목표에 도달하면 대시가 끝나지만 **그 자리에 멈추지 않는다.** 같은 방향으로 30~80포인트를
평소 속도로 더 걸어 나간다. 90pt/s 에서 한 프레임 만에
0이 되면 부자연스럽다. 시작할 때 그 방향으로 60포인트도 못 가면
반대 방향을 쓰고, 양쪽 다 좁으면 대시하지 않는다.

**벽은 뚫지 못한다.** 부딪혔을 때의 반응은 속도에 따라 다르다.

**띠 끝에서는 아무 일도 일어나지 않는다.** 목표를 띠 안에서 고르므로 캐릭터는 목표에
도달하고 다음 목표를 새로 잡을 뿐이다. 끝에 닿았는지 검사하지 않는다. 띠 끝은 사람마다
위치가 다르므로 거기서 다치면 동료 화면에서는 아무것도 없는 자리에서 다치는 것처럼 보인다.

낙하 피격의 기준을 500pt/s 로 잡은 이유는 점프와 구분하기 위해서다. 정점 48포인트에서
떨어지면 약 320pt/s 이므로 스스로 뛴 것으로는 다치지 않는다. 약 114포인트보다 높은 데서
떨어져야 걸린다. 드래그로 들어 올려 놓았을 때가 여기에 해당한다.

**낙하 속도는 최고 높이에서 구한다.** 자유낙하는 `v = √(2gh)` 이므로 프레임 타이밍과
무관하고 원격 캐릭터에도 그대로 적용된다.

프레임 간 높이 변화로 계산하면 안 된다. 한 프레임에 50pt 넘게 떨어지므로 착지 직전 프레임의
높이가 0~50 사이 아무 값이나 되고, 같은 높이에서 떨어져도 결과가 열 배 넘게 널뛴다.
`verticalSpeed` 도 쓸 수 없다. 착지 직전에 0으로 초기화되고 원격 캐릭터에는 아예 없다.

대시 충돌과 같은 반응이라 별도 처리가 없다. 피격 중에는 이동이 멈추므로 벽에서 튕겨 나온
것처럼 보인다.

동작은 상태를 따로 두지 않고 매 프레임 조건으로 정한다.

| 조건 | 동작 |
|---|---|
| 드래그로 들려 있음 | 대기 첫 프레임에서 정지 |
| 피격 중 (0.6초) | 피격 |
| `y > 0` | 점프 |
| 가로 속도 > 70pt/s | 대시 |
| 이동 중 | 걷기 |
| 그 외 | 대기 |

들려 있는 동안 점프 동작을 재생하면 스스로 뛰는 것처럼 보인다. 잡혀 있는 것이므로
가만히 서 있게 둔다. 놓는 순간부터 낙하이므로 점프 동작이 나온다.

가로 속도로 판정하므로 드래그로 빠르게 옮길 때도 대시가 나온다.

**방향은 실제 이동량에서 뽑는다.** 산책·대시·낙하·보간 어느 경로로 움직이든 같은 기준을
쓴다. 스프라이트는 **오른쪽을 향해** 그려져 있으므로 왼쪽으로 갈 때 뒤집는다(`xScale = -1`).

**바닥에 있을 때만 방향을 갱신한다.** 드래그로 들려 있거나 점프·낙하로 공중에 있는 동안에는
그 전 방향을 유지한다. 마우스를 좌우로 흔들 때마다 얼굴이 돌아가면 잡혀 있는 물체가 아니라
스스로 움직이는 것처럼 보이고, 떨어지는 중에 방향이 바뀌면 허공에서 몸을 튼 것처럼 보인다.
4.3 의 정지 자세와 같은 이유다.

### 4.4 대시 충돌

**평소에는 캐릭터끼리 그대로 통과한다.** 겹침을 허용하는 5.4 의 결정과 같다.

예외는 하나다. **앞으로 빠르게 나아가는 캐릭터 둘이 서로를 향하다 22포인트 안으로 들어오면
둘 다 0.6초간 피격 동작을 재생하고 멈춘다.** 서로 멀어지는 방향이면 판정하지 않는다.

판정 기준은 **표시 중인 동작이 아니라 실제 가로 속도**다.

| | 기준 |
|---|---|
| 바닥 | 70pt/s 초과 — 대시만 해당하고 산책(20pt/s)은 빠진다 |
| 공중 | 35pt/s 초과 — 걷기 점프(45)와 대시 점프(140)가 해당하고 제자리 점프는 빠진다 |

동작 이름으로 판정하면 대시 점프가 빠진다. `y > 0` 이 속도보다 먼저 검사되어 표시 동작이
`점프` 가 되기 때문이다. 표시용 값이 판정에 새어 들어오면 이런 구멍이 생긴다.

드래그로 들려 있거나 이미 피격 중이면 판정에서 제외한다.

좌표는 모두가 공유하므로 각 클라이언트가 같은 판정을 내린다. 충돌을 알리는 메시지를
따로 두지 않는다. 보간 차이로 판정 시점이 조금 어긋날 수 있으나 표시만의 문제다.

### 4.5 이름 표시

**이름은 항상 표시한다.** 몸통 색이 12가지뿐이라 색만으로는 누구인지 알 수 없고, 커서를
올려야 이름이 나오면 화면을 훑어보는 것만으로는 누가 있는지 파악할 수 없다.

대가는 있다. 이름표가 16포인트 캐릭터보다 훨씬 넓어서, 거점이 몰린 구간에서는 이름표끼리
포개진다. 실사용에서 거슬리면 겹치는 이름표를 세로로 어긋나게 배치하거나 커서 근접 표시로
되돌린다.

`SKLabelNode`, 시스템 폰트 10pt. **반투명 검정 배경**(알파 0.55, 모서리 반경 3)을 뒤에 둔다.
밝은 바탕 위에서는 흰 글자만으로 읽히지 않는다. 배경은 이름이 바뀔 때만 다시 만든다. 캐릭터는 바닥에 서 있으므로 이름을 아래에 배치하면 Dock 에
가려지거나 화면 밖으로 나간다. 아래부터 **캐릭터 → 이름 → 말풍선** 순으로 쌓는다.

### 4.6 말풍선

- 최대 너비 200포인트, 최대 3줄, 초과분은 말줄임표로 처리한다
- 5초간 표시한 뒤 사라진다
- 씬 경계를 벗어나지 않도록 위치를 제한한다

### 4.7 바닥 그림자

캐릭터 발밑에 픽셀 타원 그림자를 표시한다. 검정 알파 0.3 이다.

**크기는 캐릭터마다 다르다.** 대기 자세에서 불투명한 픽셀의 가로 범위를 재서 그만큼의
픽셀 폭으로 타원을 만들고, 높이는 폭의 0.37배다. 레퍼런스 도트 그림에서 잰 비율이다.

**필요한 픽셀 수만큼 타원을 새로 만든다.** 고정 크기 텍스처를 늘리면 배율이 정수가 아니어서
어떤 픽셀은 2포인트, 어떤 픽셀은 1포인트로 그려지고 캐릭터의 격자와 어긋난다. 만든 텍스처는
크기별로 캐시하고 캐릭터와 같은 2배로 그린다.

프레임 폭을 쓰면 안 된다. 프레임에는 대시 자세가 옆으로 삐져나온 여백이 들어 있어, 실제 몸이
15칸인 캐릭터의 프레임이 22칸이 된다. 그대로 쓰면 그림자가 몸보다 1.3배 넓어진다.

| 캐릭터 | 몸 너비 | 그림자 |
|---|---|---|
| 염소 | 15칸 | 15×6픽셀 = 30×12pt |
| 새 | 14칸 | 14×5픽셀 = 28×10pt |
| 개구리 | 10칸 | 10×4픽셀 = 20×8pt |

**그림자는 스프라이트에 넣지 않고 바닥에 고정한다.** 스프라이트의 일부로 그리면 점프할 때
캐릭터를 따라 공중으로 같이 올라간다. 캐릭터 노드의 자식이되 `y` 만큼 반대로 내려
언제나 바닥에 남게 한다. 발보다 2포인트 아래에 두어 캐릭터가 그림자를 밟고 선 것처럼 보이게 한다.

높이에 따라 줄어든다. 120포인트에서 최소가 된다.

**크기는 네 단계로 나눈다.** 배율 1 · 0.85 · 0.7 · 0.55 이고 단계마다 그 크기의 타원을
따로 만든다. 연속 배율로 줄이면 픽셀 크기가 들쭉날쭉해져 캐릭터의 격자와 어긋난다.

불투명도는 `0.3 × (1 − 비율)` 로 연속 변화시킨다. 알파에는 격자 문제가 없다.

| 높이 비율 | 염소(몸 15칸) |
|---|---|
| 0 ~ 0.25 | 15×6픽셀 = 30×12pt |
| 0.25 ~ 0.5 | 13×5픽셀 = 26×10pt |
| 0.5 ~ 0.75 | 10×4픽셀 = 20×8pt |
| 0.75 ~ 1 | 8×3픽셀 = 16×6pt |

그림자가 작아지고 옅어지면 점프한 높이가 눈에 들어온다. 캐릭터만 위아래로 움직이면 얼마나
떴는지 알기 어렵다.

모든 캐릭터에 같게 적용하므로 사용자가 편집하는 16×16 안에 넣지 않는다.

### 4.8 움직임

캐릭터의 안정 상태는 바닥이다. 바닥을 벗어나는 경우는 스스로 하는 점프, 드래그로 들려 있는
상태, 그리고 그 뒤의 낙하뿐이며 모두 바닥으로 되돌아온다.

**화면이 곧 공간이다. 카메라를 두지 않는다.** 캐릭터는 자기 띠 안에서만 돌아다니고,
화면이 넓은 사람은 그만큼 넓게 논다. 화면이 좁은 동료에게는 내가 자주 화면 밖에 있게 되는데,
그것을 받아들인 결과다.

맵을 화면보다 넓게 잡고 카메라로 따라가는 방식도 만들어 봤으나 되돌렸다. 좌표를 비율로
바꾸는 방식은 더 일찍 빠졌다 — 화면 폭이 2.7배 차이 나면 같은 걷기가 상대 화면에서 2.7배
속도로 보이고, 걷기 스프라이트의 다리 움직임과 어긋나 발이 미끄러진다. 속도를 함께
비율로 바꾸면 캐릭터 크기도 비율이 되어야 하고, 그러면 2배 정수 스케일이 깨진다.

**캐릭터 설정 창이 열려 있는 동안에는 제자리에 선다.** 색을 고르는 사이에 걸어가 버리면
결과를 볼 수가 없다. 공중에 있으면 착지한 뒤에 선다 — 그러지 않으면 공중에 멈춘다.

**거점이 없다.** 캐릭터는 띠 전체를 자유롭게 돌아다닌다. 움직임은 **대기·걷기·뛰기** 세
상태의 전이로 정한다. 한 구간이 끝나면 방향을 먼저 정하고 다음 상태를 고른다.

**방향**

| 현재 | 가던 방향 유지 | 반대 |
|---|---|---|
| 대기 | — | 좌우 50:50 |
| 걷기 | 80% | 20% |
| 뛰기 | 90% | 10% |

서 있다 출발할 때는 방향을 가리지 않는다. 뛰던 중에는 관성이 커서 방향을 잘 바꾸지 않는다.

다음 상태를 먼저 고르고 방향을 정한다. 고른 방향에 그 상태의 최소 거리(걷기 80, 뛰기 200)가
안 남았으면 반대로 간다. 양쪽 다 200포인트를 못 채우면 뛰지 않고 걷는다.

**다음 상태**

| 현재 | 걷기 | 뛰기 | 대기 |
|---|---|---|---|
| 대기 | 70% | 30% | — |
| 걷기 | 70% | 15% | 15% |
| 뛰기 | 70% | 15% | 15% |

걷기와 뛰기의 다음 상태 분포는 같다. 전력질주는 방향 유지 확률(90%)로만 구분한다.

**구간 크기**

| | 속도 | 거리·시간 |
|---|---|---|
| 걷기 | 20 pt/s | 80~250pt |
| 뛰기 | 90 pt/s | 200~420pt |
| 대기 | — | 4~8초 |

뛰기를 시작하면 절반의 확률로 0.4~1.1초 뒤 점프를 예약한다. 그래야 대시 점프가 나온다.

동료 캐릭터는 이 계산을 하지 않는다. 수신한 좌표를 보간할 뿐이다.

드래그로 놓은 자리도 머무는 곳이 아니라 거기서부터 다시 돌아다니는 출발점이다.

#### 세로 운동

점프와 낙하는 같은 물리를 사용한다. 위로 향하는 초기 속도가 주어지는지, 들려 있던 높이에서
시작하는지만 다르다.

**물리도 전송도 포인트 단위다.** 화면 높이로 정규화하면 같은 점프가 화면마다 다른 높이로
보인다. 900pt 화면에서 캐릭터 1.5배를 뛴 것이 1200pt 화면에서는 2배로 표시된다.

**등가속도 공식으로 적분한다.** 속도만 더하는 정수 적분은 프레임 간격에 따라 정점이 달라진다.
12fps 에서는 목표 48pt 가 실제 24pt 로 줄어 캐릭터 키도 넘지 못했다.

```
y    += 속도 * dt - 0.5 * 중력 * dt * dt     (pt, 바닥이 0)
속도 -= 중력 * dt                            (pt/s)
y <= 0 이면 y = 0, 속도 = 0, 착지
```

- 중력은 1100 pt/s^2 로 지정한다. 화면 상단(약 800pt)에서 바닥까지 1.25초쯤 걸린다
- 점프가 0.5초 남짓 보인다. 이보다 짧으면 눈에 남지 않는다
- 착지 효과는 두지 않는다. 스프라이트 시트의 동작만으로 충분하다
- 세로 운동 중에는 산책을 중단한다

#### 점프

캐릭터는 **30~90초마다 한 번 스스로 점프한다.** 간격은 캐릭터마다 무작위로 결정한다.

점프는 **세 가지**이며 뛰는 시점의 상태로 정해진다.

| | 정점 | 체공 | 가로 이동 |
|---|---|---|---|
| 제자리 | 48pt | 0.59s | 0 |
| 걷기 중 | 52pt | 0.61s | 46pt |
| 대시 중 | 72pt | 0.72s | 101pt |

**공중에서도 가로 속도를 유지한다.** 이 값이 없으면 어떤 상태에서 뛰어도 제자리 점프가 된다.
벽에 닿으면 가로 속도만 0이 되고 낙하는 이어진다.

대시 점프는 점프 주기(30~90초)만 기다리면 대시(15~45초, 지속 2~5초)와 겹칠 일이 거의 없다.
**대시를 시작할 때 절반의 확률로 0.4~1.1초 뒤 점프를 예약한다.**

**착지하면 그 자리에서 새 구간을 고른다.** 가로 이동이 46~101포인트라 점프 전의 목표를
지나쳐 착지할 수 있다. 예전 목표를 그대로 두면 되돌아가려고 뒤돌아 걸어서, 뛴 방향과
반대로 얼굴이 돌아간다.

착지 뒤의 방향은 **가던 방향으로 고정한다.** 전이표의 방향 확률(80/90%)을 적용하지 않는다.
공중에서 나아간 것을 되무를 이유가 없다. 다음 상태는 전이표대로 걷기·뛰기·대기에서 고른다.
그 방향에 구간 최소 거리가 안 남았을 때만 반대로 간다.

제자리 점프는 가로 이동이 없으므로 새로 고르지 않고 대기를 이어 간다.

들려 있거나 이미 공중에 있으면 점프하지 않는다.

인원이 50명이면 화면 어딘가에서 1초에 한 번꼴로 점프가 보인다. 작업을 방해하지 않으면서
캐릭터들이 살아 있다는 느낌을 준다.

#### 드래그

**드래그는 가로와 세로 모두 반영한다.** 커서를 따라 공중으로 들어 올릴 수 있다.

**집어 드는 순간 진행 중이던 운동을 모두 지운다.** 세로 속도·공중 가로 속도·대시 목표·피격
상태를 초기화한다. 남겨두면 놓는 순간 이전 속도로 튀어 나가거나 하던 대시를 이어서 한다.

**드래그 중에는 착지를 판정하지 않는다.** 커서를 바닥까지 빠르게 내리면 낙하로 오인해
피격이 발동한다.

**놓으면 떨어진다.** 위 물리로 바닥까지 내려오고, 착지한 지점의 `x` 가 새 거점이 된다.
다른 화면으로 끌어다 놓으면 그 화면의 바닥에 착지한다.

들어 올릴 수 있는 것은 내 캐릭터뿐이다.

## 5. 좌표 모델과 다중 디스플레이

캐릭터 위치는 **바닥 띠 왼쪽 끝으로부터의 거리 `x`** 와 **바닥으로부터의 높이 `y`** 다.
**둘 다 포인트 단위 절대값이고 정규화하지 않는다.** 화면 인덱스는 공유하지 않는다.

정규화하지 않는 이유는 5.2 의 벽 규칙 때문이다. 비율로 공유하면 모든 캐릭터가 항상 모두의
화면 안에 들어와 "화면 밖으로 걸어 나간다"는 상태 자체가 존재할 수 없다.

**바닥에 있으면 `y` 를 전송하지 않는다.** 점프·낙하·드래그, 즉 `y > 0` 인 동안에만 값이
포함된다. 0.1초 주기라 0.72초짜리 점프에 표본이 7개 잡히므로 6.4 의 보간이 그대로
처리하고, 동료 화면에서도 뛰어오르고 떨어지는 모습이 그대로 보인다.

### 5.1 바닥 띠

화면들을 가로로 이어 붙여 연속된 바닥 띠 하나를 만든다. **원점은 띠의 왼쪽 끝이다.**

1. **세로 범위가 겹치는 화면끼리 한 행으로 묶는다.** 높이가 어긋나게 나란히 둔 것도
   조금이라도 겹치면 같은 행이다
2. **행은 아래부터, 행 안에서는 왼쪽부터** 잇는다
3. `x = 0` 은 맨 앞 화면의 왼쪽 모서리다. 좌표는 언제나 양수다
4. 주 디스플레이는 순서에 관여하지 않는다. 화면이 사라졌을 때 캐릭터를 데려갈 곳으로만 쓴다

**나란히 놓인 화면은 띠에서도 나란히 둔다.** 가로 중심만으로 정렬하면 아래 행의 화면이
위 행의 맞닿은 두 화면 사이로 끼어들어, 베젤을 맞대고 있는 두 화면이 띠에서 갈라진다.
그러면 A 에서 B 로 걸어갈 때 중간에 엉뚱한 화면을 지나간다.

아래 행을 먼저 두면 대개 노트북인 주 화면이 띠 앞쪽에 와서, **모니터를 빼도 주 화면
구간이 움직이지 않는다.** 좌표가 밀리는 폭이 가장 작아진다.

위아래로 쌓인 화면 사이는 어떻게 이어도 화면 이동이 점프다. 물리적으로 좌우로 걸어갈 수
없는 배치이기 때문이다. 바닥이 하나로 유지되므로 누군가 공중에 뜨는 일은 없다.

#### 원점을 띠 왼쪽 끝으로 잡는 이유

**좌우 방향이라는 개념을 없애기 위해서다.** 원점을 주 디스플레이에 붙이면 보조 모니터를
왼쪽에 둔 사람과 오른쪽에 둔 사람의 띠가 서로 반대로 뻗는다. 주 화면끼리는 겹치지만
보조 화면끼리는 전혀 겹치지 않아, 보조 모니터에 있는 동안 서로 보이지 않는다.

띠 왼쪽 끝을 원점으로 삼으면 **배치가 달라도 화면 개수와 폭이 같으면 띠가 같아진다.**
네 가지 흔한 구성으로 모든 조합의 겹침을 계산한 결과다.

| | 평균 가시성 |
|---|---|
| 주 디스플레이 기준 | 80% |
| **띠 왼쪽 끝 기준** | **100%** |

**대가는 화면 구성이 바뀔 때 좌표계가 통째로 움직인다는 것이다.** 모니터를 빼면 남은
화면이 앞으로 당겨져 같은 좌표가 다른 자리를 가리킨다. 그래서:

- **내 캐릭터는 있던 화면의 같은 자리를 지킨다.** 바뀌기 전의 전역 화면 좌표를 받아 두고
  새 띠에서 되찾는다. 좌표값은 바뀌지만 눈에 보이는 위치는 그대로다
- **있던 화면이 사라졌으면** 그 화면 안에서의 가로 위치를 지켜 주 디스플레이로 데려온다.
  화면 왼쪽에 있었으면 왼쪽에 놓인다. 주 화면이 더 좁으면 그 안으로 제한한다
- **동료 캐릭터는 내 화면에서 한 번 이동한다.** 모니터를 꽂고 빼는 것은 사용자가 의도한
  행동이고 그 순간 데스크톱 자체가 재배치되므로 그대로 받아들인다

**시작 위치는 바닥 어디든 무작위로 고른다.** 띠를 알아야 정할 수 있으므로 화면을 붙이는
시점에 한 번만 한다. 설치 식별자 해시로 정하던 방식은 원점을 왼쪽 모서리로 옮기면서
버렸다 — 고정 구간 `[-400, 400)` 이 주 화면이 맨 왼쪽인 사람에게는 절반이 띠 밖이라
왼쪽 끝에 몰린다.

### 5.2 가시 범위

**원점만 전원이 공유한다. 양 끝은 사람마다 다르다.**

- **내 캐릭터는 `[minX, maxX]` 안에만 있는다.** 산책·대시 목표를 그 안에서 고르고 좌표를
  갱신할 때 한 번 더 제한한다. 끝에 닿았을 때의 특별한 반응은 없다
- **동료가 내 띠에서 완전히 벗어나면 표시하지 않는다.** 판정은 스프라이트 폭을 포함한다.
  중심 좌표만으로 판정하면 절반이 아직 화면 안인데 통째로 사라진다
- 제한은 각자 자기 캐릭터에만 적용한다

데스크톱이 넓은 사람은 더 멀리 걸어갈 수 있고 더 많은 동료를 본다. 좁은 화면을 쓰는 사람은
멀리 간 동료를 보지 못한다. **화면 구성이 바뀌면 위치를 새 띠 안으로 당기기만 한다.** 거점으로 되돌리면 노트북을
열고 닫거나 모니터를 뺄 때마다 캐릭터가 순간이동한다.

- 내 캐릭터가 사라진 화면 구간에 있었으면 새 띠 안으로 끌려온다
- 동료가 내 새 띠를 벗어나면 그리지 않는다. 다시 연결하면 돌아온다
- **화면이 하나도 없는 순간에는 좌표를 건드리지 않는다.** 띠 길이가 0이면 제한 결과가
  전부 0이 되어 위치를 잃는다. 전환 중 일시적으로 이 상태가 될 수 있다

**시작 위치만 원점에서 ±400pt 안에 분산시킨다.** 이후로는 자유롭게 돌아다니므로 위치를
저장하지 않는다.
가장 좁은 노트북에서도 들어오는 범위라 처음에는 누구에게나 보인다.

### 5.3 표시 좌표 환산

```
x 를 누적 폭과 비교해 해당 화면과 화면 안 위치를 구한다
스프라이트 폭을 포함해 내 띠에서 완전히 벗어났으면 표시하지 않는다 (5.2)
→ 바닥 높이 = screen.visibleFrame.minY + 바닥 띄움(8pt) + 스프라이트 높이 / 2
→ 표시 좌표 = (screen.visibleFrame.minX + 화면 안 위치,
              바닥 높이 + min(y, screen.visibleFrame.height - 스프라이트 높이))
```

위 식은 전역 화면 좌표를 구한다. 오버레이 윈도우의 씬은 자기 로컬 좌표계를 사용하므로
**`screen.visibleFrame.origin` 을 빼서 씬 좌표로 변환한다.** 3.1 에서 윈도우 프레임을
`visibleFrame` 과 같게 지정했으므로 이 차감만으로 끝난다.

`visibleFrame` 을 사용하므로 캐릭터는 Dock 위에 선다. 거기서 **8포인트 더 띄운다.**
그대로 두면 Dock 이나 화면 끝에 딱 붙어 보인다.

화면마다 별도의 윈도우와 씬이므로 **경계를 넘을 때 노드를 씬 사이에서 옮겨야 한다.** 갱신할
때마다 이 환산이 반환한 화면을 확인하고, 현재 속한 씬과 다르면 이전 씬에서 제거한 뒤 새 씬에
추가한다. 이 처리가 없으면 캐릭터가 경계에서 사라진다. 이름표와 말풍선은 캐릭터 노드의
자식이므로 함께 이동한다.

### 5.4 밀집

대부분이 1모니터를 사용하므로 캐릭터는 왼쪽 1500pt 안쪽에 모인다. 32pt × 50명 = 1600pt 로
그 구간의 폭을 넘어선다. 이름을 항상 표시하므로 실제 폭은 이름표가 지배한다.

**겹침을 허용한다.** `(x, id)` 오름차순으로 `zPosition` 을 지정해 앞뒤가 생기게 하면 사람이
많은 사무실처럼 보인다. `id` 로 동률을 해소하지 않으면 같은 `x` 에 선 두 캐릭터의 앞뒤가
프레임마다 바뀌어 깜빡인다. 위치를 로컬에서 조정하지 않으므로 **전원이 같은 배치를 본다.** 좌표가
절대값이므로 화면 크기가 달라도 보이는 범위만 다를 뿐 위치는 동일하다.

**거점 `x` 는 `UserDefaults` 에 보관한다.** `id` 가 실행마다 바뀌므로 거점까지 매번 새로
정하면 드래그로 자리를 잡아도 재시작할 때마다 엉뚱한 곳에 나타난다. 보관된 값이 내 띠 길이를
넘으면(모니터를 분리한 경우) 벽 안쪽으로 제한한다.

## 6. 네트워크

### 6.1 발견

전원이 `_offiky._tcp` 서비스를 광고하면서 동시에 탐색한다. Network.framework 에서
Bonjour 광고는 `NWListener` 가 담당하므로 **모든 피어가 리스너를 연다.** 리스너를 열지 않은
피어는 발견되지 않아 선출 대상 집합에 포함되지 않는다.

방화벽 승인은 앱당 한 번이고, Developer ID 서명 앱은 기본 설정에서 자동 허용된다.

TXT 레코드: `id`, `pv`(프로토콜 버전)

**이름은 TXT 에 포함하지 않는다.** 연결하기 전에는 필요 없고, TXT 와 `hello` 양쪽에 두면
어느 쪽이 우선인지 정해야 한다. 이름의 출처는 `hello` 와 `profile` 하나뿐이다.

`id` 는 **앱을 실행할 때마다 새로 생성하는 UUID** 다. 설치 고유 값이 아니다. 이 선택이
두 가지 문제를 동시에 해결한다.

- 선출 기준이 로컬 시계에 의존하지 않는다. 시각이 어긋난 맥 하나가 영구 호스트가 되는
  상황이 발생하지 않는다.
- 채팅 일련번호 `seq` 가 항상 새 `id` 와 함께 0부터 시작하므로, 재접속 후 메시지가
  "이미 본 번호"로 판정되어 전부 무시되는 문제가 발생하지 않는다.

이름과 스프라이트는 `UserDefaults` 에 보관하므로 재시작해도 유지된다.

### 6.2 호스트 선출

투표 프로토콜은 없다. 모든 피어가 보이는 피어 목록을 **`id` 문자열 오름차순**으로 정렬하고
맨 앞을 호스트로 계산한다. 같은 목록을 보면 같은 답이 나온다.

- 자신이 호스트면 들어오는 연결을 수락하고 중계를 시작한다
- 아니면 호스트에게 `NWConnection` 을 연결한다
- **자신이 호스트가 아닌데 연결이 들어오면 즉시 종료한다.** 전원이 리스너를 열고 있으므로
  분열 구간에 이런 연결이 발생한다. 종료하면 상대가 재계산해 올바른 호스트로 이동한다
- 피어 목록 변경 후 **300ms 디바운스**를 적용하고 재계산한다. 여러 명이 동시에 합류·종료할 때
  연쇄 재연결을 방지한다

**연결이 끊어진 피어는 Bonjour 목록에서 사라지기를 기다리지 않고 즉시 후보에서 제외하고
재계산한다.** 호스트가 비정상 종료하면 mDNS TTL 만료까지 수십 초가 걸리므로, 이 처리가
없으면 그 시간 동안 전원이 멈춘다. 제외 상태는 10초간 유지한 뒤 해제한다.

**제외할 때 그 피어의 캐릭터도 지운다.** 클라이언트 이탈은 호스트가 감지해 `leave` 를
전파하지만, 호스트 이탈은 감지하는 주체가 없다. 지우지 않으면 그 캐릭터가 마지막 위치에
남고, 그 사람이 앱을 다시 켜면 `id` 가 새로 발급되어 같은 사람이 두 명으로 보인다. 새
호스트가 된 쪽의 프로필 목록에도 남아 이후 접속자에게 `join` 으로 전파된다.

**우리가 직접 끊는 연결은 상태 핸들러를 떼고 끊는다.** 호스트 교체와 절전 진입에서 기존
연결을 종료하는데, 핸들러가 살아 있으면 `cancelled` 가 이탈 처리로 이어져 멀쩡한 피어를
지운다. 이탈 처리는 상대가 실제로 끊었을 때만 돌아야 한다.

**네트워크 경로가 바뀌면 메시를 다시 시작한다.** `NWPathMonitor` 로 감시한다. Wi-Fi 를
바꾸거나 이더넷을 뽑으면 열어 둔 리스너와 연결이 쓸모없어지는데, 절전 복귀와 달리 알려 주는
알림이 없다. 전환 중에는 알림이 여러 번 오므로 1초 기다렸다가 실행한다.

**리스너와 브라우저가 실패하면 같은 경로로 다시 시작한다.** 리스너가 죽으면 광고가 멈춰
아무도 연결하지 못하는데, 화면에는 아무 표시가 없다. 자신이 호스트였다면 전원이 고립된다.

다시 시작할 때 이전 연결의 흔적을 모두 지운다. 남겨 두면 다시 붙을 때까지 멈춘 캐릭터가
화면에 남는다. 우리가 직접 끊는 연결은 언제나 상태 핸들러를 떼고 끊는다 — 그러지 않으면
`cancelled` 가 이탈 처리나 재시작을 다시 부른다.

**프로토콜 버전이 다른 피어는 후보에서 제외하고 그 수를 메뉴에 표시한다.** 광고의 TXT
레코드에 이미 버전이 들어 있으므로 연결하기 전에 판별한다.

제외하지 않으면 옛 버전이 호스트로 뽑혔을 때 새 버전 사용자 전원이 아무도 보지 못한다.
호스트는 `hello` 의 버전이 다르면 응답하지 않는데, 클라이언트 쪽에는 그 사실이 전달되지
않아 앱이 고장 난 것처럼 보인다. 표시가 없으면 사용자가 원인을 알 수 없다.

**제외가 풀리는 시점에 재계산을 예약한다.** `elect` 는 Bonjour 목록이 바뀔 때만 불리므로,
목록이 그대로면 제외가 만료돼도 아무도 깨우지 않는다. 서로를 제외한 둘이 각자 자기를
호스트로 믿고 앉아 있으면 그 상태가 영원히 지속된다 — 화면에 아무도 안 보인다.
호스트가 바뀌는 구간에는 서로를 거절하며 제외가 쌓이므로 실제로 일어난다.

**같은 피어가 두 경로로 붙는 일이 있다.** 하나가 끊겼다고 피어를 지우면 캐릭터가 사라진다.
남은 연결이 있는지 확인하고 지운다.

두 명이 동시에 자신을 호스트로 판단하는 구간이 잠깐 발생할 수 있다. 목록이 수렴하면
해소되고, 그 사이 잘못 연결된 클라이언트는 다음 재계산에서 이동한다.

`id` 가 실행마다 바뀌므로 호스트 역할은 자연히 분산된다.

### 6.3 프로토콜

줄바꿈으로 구분한 UTF-8 JSON 이다. `Codable` 로 처리하고 `nc` 로 직접 확인할 수 있다.

클라이언트 → 호스트:

```
{"t":"hello","pv":1,"id":"...","name":"Kyle","sprite":"...16줄..."}
{"t":"pos","x":862.5}
{"t":"pos","x":862.5,"y":48}       y > 0 인 동안에만 포함한다. 둘 다 포인트
{"t":"say","seq":7,"msg":"점심 먹으러 갈 사람"}
{"t":"profile","name":"Kyle","sprite":"...16줄..."}
```

호스트 → 클라이언트:

```
{"t":"join","id":"...","name":"Kyle","sprite":"...16줄..."}
{"t":"leave","id":"..."}
{"t":"snap","p":[{"id":"...","x":862.5},{"id":"...","x":1204,"y":48}]}
{"t":"say","id":"...","seq":7,"msg":"점심 먹으러 갈 사람"}
{"t":"ack","seq":7}
{"t":"profile","id":"...","name":"Kyle","sprite":"...16줄..."}
```

버전 필드는 `pv` 를 사용한다. 좌표 `x`·`y` 와 혼동하지 않기 위해서다.

새로 접속한 클라이언트에게는 호스트가 **알고 있는 피어 수만큼 `join` 을 연속 전송한다.**
별도의 명부 메시지 형식을 두지 않는다.

### 6.4 위치 전파

- 클라이언트는 **0.1초마다** 자기 좌표를 전송한다. 상태에 따라 주기를 바꾸지 않는다
- 호스트는 0.1초마다 전원의 좌표를 담은 스냅샷 하나를 각 클라이언트에게 전달한다.
  **호스트 자신의 좌표도 스냅샷에 포함된다.**
- **호스트는 받은 좌표를 중계만 하지 말고 자기 화면에도 반영한다.** 자기가 보낸 스냅샷은
  받지 않으므로, 이 처리가 없으면 호스트 화면에서 클라이언트 캐릭터가 접속한 자리에 멈춘다
- 유실되어도 다음 스냅샷이 덮어쓰므로 재전송하지 않는다

**주기를 0.5초로 두면 점프를 표현할 수 없다.** 점프는 0.72초라 표본이 한두 개만 잡힌다.
`y > 0` 인 동안에만 빨리 보내는 방식도 소용이 없었다 — 중계 주기가 0.5초 고정이라
보낸 것의 대부분이 호스트에서 버려졌다.

#### 보간: 항상 과거를 그린다

수신 측은 **받은 표본 두 개 사이를 재생한다.** 최신 좌표를 향해 다가가는 방식이 아니다.

렌더 시각은 `현재 - 0.3초` 다. **간격이 아니라 실측한 편차로 정한다.** 0.1초 주기로
보낸 좌표가 Wi-Fi 에서 최대 0.21초, 드물게 0.4초 만에 온다. 지연이 그보다 짧으면 버퍼가
바닥나 캐릭터가 한두 프레임 얼어붙고, 대시처럼 빠른 동작에서 끊겨 보인다.
0.2초일 때 프레임의 1~5% 가 굶었고 0.3초에서 0% 가 됐다.
그 시각을 감싸는 두 표본을 골라 사이를 선형 보간한다. **앞뒤 끝점을 모두 쥐고 있으므로
추정하지 않는다.** 0.2초 지연은 주변 캐릭터에게는 보이지 않는다.

최신 좌표를 향해 고정 시간 동안 다가가는 방식은 쓰지 않는다. 도착하기 전에 다음 좌표가
와서 매번 다시 시작하므로 목표에 영영 닿지 못하고 뒤처진 채 기어간다. 좌표를 자주 받을수록
더 심해져서, 0.1초마다 직접 받는 호스트 화면이 가장 느리게 보인다.

표본이 끊기면 마지막 자리에 세워 둔다. 외삽하지 않는다.

#### 스냅샷 크기

**좌표에는 `id` 대신 번호를, 실수 대신 정수를 싣는다.** 한 건이 `[번호, x]` 또는
`[번호, x, y]` 다. 바닥에 있으면 `y` 를 생략한다.

번호는 호스트가 접속 순서대로 부여하고 `join` 에 실어 전파한다. 36자 UUID 가 한두 자로
줄어든다. 호스트가 바뀌면 번호 체계가 새로 시작되므로 양쪽 모두 대응표를 비운다. 번호를
모르는 좌표는 버린다 — 다음 `join` 이 오면 저절로 복구된다.

좌표를 포인트 단위 정수로 내림해도 **화면에 나타나지 않는다.** 표시 위치를 어차피 2포인트
격자에 맞추므로 정밀도가 표시보다 두 배 촘촘하다.

| 50명 스냅샷 1건 | 한 건 | 호스트 업로드(0.1초 주기) |
|---|---|---|
| id + 실수 좌표 | 58B | 2920B → 1397KB/s |
| **번호 + 정수** | **11B** | **536B → 256KB/s** |

5.4배 작아진다. 50명이 동시에 접속해도 256KB/s(2Mbps)라 Wi-Fi 에서 무리가 없다.

더 줄일 여지는 남아 있고 필요해지면 그때 한다 — 보이는 범위 밖의 피어를 빼거나(화면이
좁을수록 효과가 크다), 직전 스냅샷과 달라진 것만 보내거나, 프레이밍을 길이 접두사로 바꿔
JSON 없이 5바이트로 싣는 방법이 있다.

전원을 담은 스냅샷을 유지하는 이유는 유실과 순서 뒤바뀜에 저절로 복구되기 때문이다.
송신량이 실제로 문제가 되면, 직전 스냅샷 이후 좌표가 변한 피어만 포함하고 5초마다 전체를
전송해 재동기화하는 방식으로 전환한다. 캐릭터는 대부분 정지해 있으므로 평상시 송신량이
10분의 1 수준으로 줄어든다. 측정 전에는 적용하지 않는다.

### 6.5 채팅 전파

- 호스트가 즉시 전원에게 전달하고 발신자에게 `ack` 를 반환한다
- 클라이언트는 `ack` 를 받을 때까지 메시지를 대기열에 보관하고, **호스트가 교체되면 새
  호스트에게 재전송한다.** 중계자가 바뀌는 순간에 메시지가 조용히 사라지는 것이 이 구조에서
  가장 눈에 띄는 실패라서 여기만 재전송을 적용한다
- **호스트 자신이 보낸 메시지는 즉시 전파되므로 대기열과 `ack` 를 사용하지 않는다**
- **대기열을 가진 클라이언트가 스스로 호스트가 되면** 재전송할 상대가 없다. 대기열의 메시지를
  자신이 직접 전원에게 전달하고 대기열을 비운다

**중복 제거**는 피어별 마지막 `seq` 정수 하나로 처리한다. `seq <= 마지막값` 이면 무시한다.
최근 기록 50개로 판정하면 51번째 이후에 도착한 늦은 재전송을 검출하지 못한다.
피어당 8바이트로 완전하게 처리된다.

### 6.6 프로필 전파

이름과 스프라이트를 **`profile` 메시지 하나로 함께 전달한다.** 둘 다 자주 바뀌지 않고 같은
시점에 필요하므로 메시지를 나눌 이유가 없다. 1.5KB 를 0.5초마다 50명분 재전송할 이유도
없으므로 위치와는 다른 경로로 전달한다.

- 접속할 때 `hello` 에 포함해 전송한다. 호스트가 보관하고 전원에게 `join` 으로 전달한다
- 편집기에서 저장하거나 이름을 변경하면 `profile` 메시지를 전송하고 호스트가 전원에게
  전달한다
- 위치 스냅샷에는 `id` 와 좌표만 포함한다

### 6.7 입력 검증

수신한 데이터는 다른 사람의 맥에서 실행되는 코드가 생성한 것이므로 신뢰할 수 없는 입력으로
처리한다. **이것이 외부 데이터가 들어오는 유일한 통로다.**

처리 기준은 둘로 나눈다. **형식이 깨진 경우에만 연결을 종료하고, 내용이 규칙을 벗어나면
대체하거나 무시한다.** 이름이 한 글자 길다고 동료의 연결을 끊을 이유가 없다.

| 대상 | 규칙 | 위반 시 |
|---|---|---|
| 메시지 1건 크기 | 16 KB 이하 | 연결 종료 |
| JSON 파싱 | 성공해야 한다 | 연결 종료 |
| `pv` | 알고 있는 버전과 일치 | 연결 종료 |
| 스프라이트 | 정확히 16줄, 각 줄 96자, 6자 단위가 `RRGGBB` 이거나 `......` | 기본 캐릭터로 대체 |
| 이름 | 1~20자, 제어 문자 제외 | 20자로 자르고 제어 문자 제거. 비면 `?` |
| 채팅 본문 | 1~200자, 제어 문자 제외 | 해당 메시지 무시 |
| 좌표 | `x` 의 절댓값이 10000 이하, `y` 가 없거나 0 이상 4000 이하 | 해당 항목 무시 |

### 6.8 샌드박스 설정

- entitlement: `com.apple.security.network.client`, `com.apple.security.network.server`
- `Info.plist`: `NSBonjourServices = ["_offiky._tcp"]`, `NSLocalNetworkUsageDescription`
- macOS 15 부터 로컬 네트워크 접근에 사용자 승인이 필요하다

**표시 이름은 `Offiky` 다.** 번들 이름과 앱 파일 이름에 쓴다. 번들 ID 는 `com.offiky.app`
그대로 둔다 — 바꾸면 설정 저장 위치가 달라져 모두의 이름과 캐릭터가 초기화된다.
Homebrew cask 이름은 관례대로 소문자 `offiky` 를 쓴다.

**빌드 번호는 표시하지 않는다.** 배포마다 버전과 함께 올라가므로 따로 알릴 것이 없다.

## 7. 채팅 입력

전역 단축키 **`⌥F`** 로 입력줄을 표시한다. Carbon `RegisterEventHotKey` 로 등록한다.
샌드박스에서 동작하고 접근성 권한이 필요 없다. SwiftUI 에는 전역 단축키 API 가 없다.

**고정값이며 사용자가 바꾸지 않는다.** 재지정 UI 를 두었다가 제거했다 — 고를 수 있게 하는
쪽이 원칙적으로는 맞지만, 실제로 쓰는 사람은 거의 없고 녹화 창과 저장·재등록 경로가 따라온다.

**기준은 타자 중에 손가락이 홈 포지션을 떠나지 않는가다.** 다른 앱에서 글을 쓰다가
그대로 채팅으로 들어가는 것이 이 단축키의 목적이다.

| 후보 | 판정 |
|---|---|
| `⌘` + 알파벳 | 26자가 사실상 전부 표준 명령에 차 있다. 전역으로 잡으면 모든 앱에서 그 기능이 죽는다 |
| `⇧F7` 같은 F키 | 맥은 기본 설정에서 `fn` 을 함께 눌러야 하고, 양손이 맨 윗줄까지 올라간다 |
| `⌃⌥Space` | macOS 의 입력 소스 전환이 선점한다 |
| `⌘.` | AppKit 이 표준 취소로 묶어두고 있고 Xcode 에서는 Stop 이다 |
| `⌥T` | 왼검지가 홈 포지션에서 윗줄로 올라간다 |
| `⌥Space` | 손가락은 안 움직이지만 Alfred 의 기본 단축키다 |
| **`⌥F`** | 왼엄지 + 왼검지. 검지는 이미 F 에 있다 |

뺏는 것은 `ƒ` 입력뿐이다.

**다른 앱이 같은 조합을 먼저 잡고 있으면 등록에 실패한다.** 알리지 않으면 사용자는 앱이
고장 난 줄 안다. 등록 결과를 확인해 실패하면 메뉴에 표시한다.

**커서가 있는 화면의 가운데 아래**에 입력줄 하나만 표시한다. Spotlight 와 같은 형태이되
위치를 아래로 내려 작업 화면을 덜 가린다.

- 가로 중앙, 세로는 `visibleFrame` 높이의 22% 지점
- 520×52 포인트, 모서리 둥근 `.ultraThinMaterial` 배경
- `styleMask: [.borderless, .nonactivatingPanel]`, `level = .modalPanel`

`borderless` 윈도우는 기본적으로 키 윈도우가 되지 않아 입력을 받지 못한다. `NSPanel` 을
상속해 `canBecomeKey` 를 `true` 로 재정의한다.

- Enter — 전송하고 숨긴다. 내 캐릭터 머리 위에 5초간 말풍선으로 표시되고 동시에 전원에게
  전달된다
- Esc — 취소하고 숨긴다
- 다른 곳을 클릭해 키 윈도우 자격을 잃으면 숨긴다 (`didResignKeyNotification`)

**닫을 때 띄우기 직전의 앱으로 포커스를 되돌린다.** 입력줄을 표시하려면 `NSApp.activate` 로
이 앱을 활성화해야 하는데, 창이 없는 메뉴바 앱이라 닫아도 포커스가 어디에도 가지 않는다.
`show` 시점의 `NSWorkspace.frontmostApplication` 을 기억했다가 되돌린다.

**`activate()` 만으로는 동작하지 않는다.** macOS 14 부터 다른 앱을 활성화하는 데 제약이
생겨 시스템이 무시한다. `NSApp.yieldActivation(to:)` 로 활성화 권한을 먼저 넘겨야 한다.

기억할 때 우리 앱이 이미 앞에 있으면 직전 값을 유지한다. 덮어쓰면 복귀 대상이 자기 자신이
되어, 한 번 실패한 뒤로는 계속 실패한다.

**다른 앱을 클릭해 닫힌 경우에는 되돌리지 않는다.** 그 앱이 이미 앞에 있으므로, 되돌리면
사용자가 방금 고른 앱에서 포커스를 도로 뺏는다.
- 표시할 때마다 내용 뷰를 새로 넣어 입력란을 비우고 포커스를 다시 잡는다

**대화를 보관하지 않는다.** 메모리 링버퍼도, 메뉴바 목록도 두지 않는다. 메시지는 말풍선으로
5초간 표시되고 사라지며 어디에도 남지 않는다.

대가는 명확하다. **자리를 비운 사이에 온 메시지는 확인할 방법이 없다.** 기록을 남기지 않는
것을 우선한 결과다.

## 8. 캐릭터 선택

메뉴바에서 "내 캐릭터…"를 선택하면 창이 표시된다.

- 9종 썸네일. 현재 색 조정을 반영해 그린다
- 색상·채도·밝기 슬라이더 세 개
- "색 초기화"
- 걷기 6프레임 미리보기

**픽셀을 직접 그리는 기능은 없다.** 16×16 격자를 손으로 찍게 하면 대부분은 기본 캐릭터를
그대로 쓰고, 그린 그림을 전송하느라 프로필 메시지가 1.5KB 가 된다. 선택과 색 조정만으로
충분한 다양성이 나오고 전송량은 수십 바이트로 줄어든다.

바꾸는 즉시 `UserDefaults` 에 저장하고 `profile` 메시지로 전파한다.

## 10. 검증

네트워크와 UI 없이 실행할 수 있도록 순수 함수로 분리해 기존 `offikyTests` 타깃에서 검증한다.

1. **호스트 선출** — 피어 목록을 입력하면 호스트 `id` 를 반환한다.
   `id` 정렬이 결정적인지, 연결이 끊어진 피어가 제외되는지, 목록이 비면 자신이 호스트가 되는지
   검증한다.
2. **바닥 환산과 벽** — `(x, y)` 와 화면 배열을 입력하면 화면과 표시 좌표를, 범위를 넘으면
   "표시하지 않음"을 반환한다. `x = 0` 이 첫 화면 왼쪽 끝에 오는지, 화면 경계값이 인접 화면으로
   정확히 넘어가는지, **띠 길이를 넘는 `x` 가 표시 대상에서 제외되는지**, 세로로 어긋나게 배치한
   모니터에서도 빈 구간이 생기지 않는지, 발신 측보다 낮은 화면에서 `y` 가 화면 안으로 제한되는지
   검증한다. 내 캐릭터의 이동이 `[0, 띠 길이 - 스프라이트 폭]` 으로 제한되는지도 함께 검증한다.
3. **중복 제거** — 호스트 교체 후 재전송된 메시지가 한 번만 표시되는지, 늦게 도착한 오래된
   `seq` 가 무시되는지 검증한다.
4. **스프라이트 인코딩** — 문자열로 변환한 뒤 되돌렸을 때 같은 그림인지, 줄 수·글자 수·허용
   문자를 벗어난 입력이 전부 거부되는지 검증한다.

나머지(윈도우 속성, SpriteKit 렌더링, 실제 Bonjour 발견, 다중 디스플레이 동작)는 맥 두 대
이상으로 직접 확인한다.

## 11. 알려진 한계와 위험

**투명 픽셀 클릭 통과는 성립하지 않는다.** 2026-09-15 실기로 확인했다. 전체 화면 투명
오버레이는 투명한 영역의 클릭까지 전부 가로채 맥을 사용할 수 없게 된다. 3.1 에 기록한 대로
오버레이를 표시 전용으로 두고 드래그용 윈도우를 따로 배치한다.

**전송이 평문이고 참가 제한이 없다.** 같은 대역대의 누구나 대화를 읽을 수 있다. 프로토콜에
`pv` 필드를 두었으므로, 나중에 TXT 레코드에 팀 키 해시를 추가하고 TLS-PSK 로 전환할 수 있다.

**부분 네트워크 장애 시 화면이 분리될 수 있다.** 특정 피어와 호스트 사이만 끊어지면 그
피어는 다른 호스트를 선택해 나머지와 분리된다. LAN 에서는 드물고 재연결되면 해소되므로
완전 해결 대신 알려진 한계로 둔다.

**mDNS 가 서브넷을 넘어가지 않으면 다른 층 사람이 보이지 않는다.** 네트워크 구성에 따른
제약이다.

**데스크톱이 넓은 사람은 좁은 화면 동료에게 보이지 않는 자리로 이동할 수 있다.** 5.2 의 벽
규칙에서 의도한 결과지만, 화면에서 사라진 것과 자리를 비운 것이 구분되지 않는다. 접속자
목록을 두지 않으므로 확인할 방법도 없다. 첫 실행 위치를 0~1200pt 로 제한하는 것이 유일한
완화책이다.

**캐릭터가 항상 작업 창 위에 표시된다.** `.floating` 레벨이므로 발표나 집중 작업에 방해가
된다. 메뉴바의 "캐릭터 숨기기" 토글이 필수 탈출구다.
