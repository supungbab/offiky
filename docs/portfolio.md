# Offiky — 만들면서 고려한 것들

> 같은 사무실 Wi-Fi 에 있는 동료들의 픽셀 캐릭터가 각자의 화면 아래를 걸어 다니는 macOS 메뉴바 앱.
> 서버 없이 LAN 안에서만 통신하고, 단축키로 말풍선 채팅을 보낸다.

| 항목 | 내용 |
|---|---|
| 기간 | 2026-09-15 ~ 2026-10-13 (약 4주, 1인 개발) |
| 규모 | Swift 약 3,600줄 · 파일 15개 · 단위 테스트 147개 · 커밋 359개 |
| 릴리스 | v1.0.0 → v2.24.0, 58회 배포 (Homebrew cask) |
| 기술 | SwiftUI `MenuBarExtra`, AppKit 투명 오버레이 창, SpriteKit, Network.framework (Bonjour · TCP · UDP), Swift Testing |
| 배포 | 자체 서명 인증서 + Homebrew tap, App Sandbox 유지 |

# 1부. 결정 기록

## 1. 문제 정의와 제약

- **대상**: 회사 맥북 사용자. 메신저를 열 정도는 아닌 가벼운 존재감과 한마디를 주고받는 용도.
- **서버를 두지 않는다.** 계정·가입·설정 없이 같은 네트워크에 있으면 서로를 찾아야 한다. 서버 비용과 운영 부담도 없앤다.
- **일을 방해하지 않는다.** Dock 에 나타나지 않고, 캐릭터 위를 클릭해도 아래 창이 클릭되어야 한다.
- **대화를 남기지 않는다.** 말풍선은 5초 뒤 사라지고, 채팅 기록은 메모리에만 두며 앱을 종료하면 지운다.
- **화면 구성이 사람마다 다르다.** 외장 모니터 개수, 세로 배치, 노트북을 덮고 쓰는 사람까지 고려해야 한다.
- **사무실 노트북은 자주 움직인다.** 잠자기, 덮개 닫기, AP 이동, Wi-Fi 변경이 하루에도 여러 번 일어난다. 이것이 네트워크 설계 전체를 좌우한 제약이었다.

## 2. 좌표 모델 — 모니터 구성이 달라도 같은 공간처럼

가장 오래 고민한 주제. "모두가 동일한 느낌"을 받으려면 어떤 좌표계를 써야 하는가.

**지킨 원칙 두 가지**
- 어떤 사람 화면에서도 캐릭터가 **순간이동하지 않는다.**
- 어떤 사람 화면에서도 캐릭터가 **공중에 떠 있지 않는다.**

**결정**
- 모든 캐릭터는 바닥에만 산다. 화면 여러 개를 **가로 한 줄의 바닥 띠(1차원)** 로 이어 붙이고, x 좌표 하나만 공유한다. 높이가 다른 바닥을 여러 개 두면 누군가의 화면에서는 떠 보이기 때문이다.
- 화면이 넓은 사람은 "맵이 넓은 사람"이다. 내 활동 범위는 내 띠 길이로만 제한하고, 화면이 좁은 동료에게는 멀리 간 캐릭터가 보이지 않을 뿐이다.
- 세로로 쌓인 모니터도 가로 띠로 펼친다. 처음에는 "주 화면 기준 어느 쪽으로 치우쳤는지"로 좌우를 정했고, 이후 **물리적으로 나란히 놓인 화면은 띠에서도 나란히** 두도록 행 단위로 묶어 정렬하는 방식으로 바꿨다.
- 원점은 주 화면 가운데 → 띠의 왼쪽 끝으로 옮겼다. 음수 좌표가 사라지고 코드가 단순해졌다.
- 시작 위치는 무작위 → 주 화면 가운데로 바꿨다. "시작할 때 어디서 나타날지 예측할 수 있어야 한다"는 이유.

**시도했다가 되돌린 것**
- **큰 맵 + 따라가는 카메라**: 구현까지 했지만 캐릭터가 화면에 고정되는 느낌이 원하는 방향이 아니어서 "화면이 곧 공간" 모델로 되돌렸다.
- **미니맵·순간이동·참가자 위치 표시**: 같은 이유로 제거.
- **화면 끝의 벽과 벽 충돌 피격**: 규칙만 복잡해져서 벽 개념을 없애고 좌표 범위 제한만 남겼다.

**모니터 연결·해제 처리**
- 보조 모니터를 뽑으면 그 화면에 있던 **내 캐릭터만** 주 화면의 같은 가로 위치로 옮긴다. 다른 사람 캐릭터는 수정하지 않는다.
- macOS 는 모니터 전환 중 화면이 0개로 보고되는 순간이 있다. 그때 다시 계산하면 위치를 잃으므로 마지막으로 보이던 자리를 따로 기억한다. 이 경로는 단위 테스트 5건으로 고정했다.
- `NSScreen.main` 은 "키보드 포커스가 있는 화면"이고 메뉴바 화면은 `NSScreen.screens[0]` 이라는 점처럼, 이름과 실제 의미가 다른 API 를 하나씩 확인했다.

## 3. 네트워크 구조 — 다섯 번 바꾼 토폴로지

이 프로젝트에서 가장 많이 바뀐 부분이다. 매번 "왜 바꾸는가"를 숫자로 비교하고 결정했다.

| 시기 | 구조 | 바꾼 이유 |
|---|---|---|
| 9/15 | **자동 선출 호스트 중계** (Bonjour 발견 + id 가 가장 작은 사람이 호스트) | 서버 없이 시작하기 위한 가장 단순한 구조 |
| 9/16 | **풀 메시** (모두가 서로 직접 연결) | 호스트 한 명에게 부하가 몰리는 것이 부담 |
| 9/21 | **호스트 + 방(최대 50명)** | 무선 환경에서는 송신자가 많은 풀 메시보다 호스트 중계가 airtime 측면에서 유리하다는 분석 |
| 9/30 | **방 안 풀 메시 (방당 15명)** | 노트북 이동·잠자기로 호스트가 너무 자주 바뀌고, 그때마다 화면이 끊김 |
| 10/1 | **채널 1~20 + 채널 안 풀 메시** | 방 만들기·대기실·방 id 관리가 Wi-Fi 이동과 맞물려 복잡해짐. 메이플스토리식 고정 채널로 단순화 |

**결정에 사용한 근거**
- **연결 수 공식**: 풀 메시는 n(n−1)/2 연결, 전송은 n(n−1)×Hz. 50명·10Hz 면 초당 24,500 패킷이고, 15명이면 2,100 패킷. 사무실 Wi-Fi 에서는 바이트 수보다 **패킷 수(airtime 경쟁)** 가 문제라는 점을 기준으로 상한을 15명으로 정했다.
- **방을 나누면 해결되는가**: 200명이 10명씩 20개 방에 나뉘면 한 사람당 연결은 9개. 인원 상한을 방 단위로 두면 전체 사용자 수와 무관하게 부하가 고정된다는 점을 확인하고 채널 구조를 택했다.
- **UDP 멀티캐스트 검토**: "허공에 외치면 다 같이 듣는" 방식은 패킷 수가 가장 적지만, 사무실 AP 가 멀티캐스트를 막거나 속도를 제한하는 경우가 많고 게임 실사례도 드물어 채택하지 않았다.
- **서버 도입 검토**: 50명 동시 접속에는 서버가 가장 낫지만, "가입도 서버도 없다"는 제품 성격을 우선해 서버 없이 최적화하는 쪽을 택했다.
- **StarCraft 의 lockstep P2P** 같은 사례와 비교해, 이 앱은 입력 명령이 아니라 위치를 주고받으므로 그대로 적용되지 않는다는 점을 정리했다.

**호스트 방식에서 다룬 문제들** (풀 메시로 가기 전까지)
- 호스트 선출 규칙: "id 가 가장 작은 사람" → "**먼저 들어온 사람이 호스트를 맡고, 다시 들어온 사람이 호스트를 빼앗지 않는다**". 게임의 방장 규칙과 같게 만들었다.
- 호스트 교체 후 아무도 안 보이던 split-brain: 제외 목록의 10초 TTL 이 끝나도 재선출이 실행되지 않아 두 사람이 모두 자신을 호스트로 판단했다. 만료 시점에 재선출을 예약해 해결.
- `NWConnection.cancel()` 뒤에도 마지막 수신 콜백이 한 번 온다는 사실을 별도 Swift 프로그램으로 증명하고, 그 콜백이 **새 호스트**를 제외하던 버그를 객체 동일성 비교로 막았다.

**풀 메시에서 새로 풀어야 했던 것**
- 중복 연결: A 와 B 가 동시에 서로를 발견하면 연결이 두 개 생긴다 → id 비교로 한쪽만 연결을 연다.
- 정원 판정의 주체가 없어진다: 동시에 두 명이 들어오면 기기마다 판정이 달라 일부와만 연결되는 문제가 생겼다 → 아직 아무와도 인사하지 않은 경우에만 나가도록 조건을 좁히고, 거절된 연결이 5초마다 무한히 다시 열리지 않도록 재시도를 중단.
- 명단 불일치, 호스트가 모아 두던 채팅 기록을 누가 보낼지 등 호스트만 갖고 있던 상태를 하나씩 목록으로 만들어 대응.

## 4. 실시간 움직임 — "온라인 게임처럼 끊기지 않게"

로컬 네트워크인데도 상대 캐릭터가 끊겨 보이는 문제를 몇 차례에 걸쳐 해결했다.

1. **과거를 그린다 (보간)**: 받은 좌표를 바로 그리지 않고, 일정 시간 전의 두 샘플 사이를 보간해서 그린다. 처음에는 외삽(추측)을 전혀 하지 않았고, UDP 로 바꾼 뒤에는 패킷 손실 몇 건을 가리려고 **최대 0.5초만** 직전 속도로 이어 그린다. 같은 자리를 다시 받으면 멈춘 것으로 판정한다.
2. **지연을 실측으로 정한다**: Wi-Fi 에서 도착 간격을 측정하니 중앙값 0.1초, 최대 0.21초(가끔 0.4초). 0.2초 지연에서는 1~5% 프레임이 비었고 0.3초에서 0% 가 되었다. 이후 **도착 간격을 따라 0.15~0.5초 사이에서 자동 조정**하는 방식으로 바꿨다.
3. **보낸 시각을 함께 보낸다**: 받은 시각 기준으로 보간하면 망이 흔들릴 때 걸음이 고르지 않다. 송신 시각을 포함해 고르게 재생한다.
4. **좌표는 UDP, 채팅·입장은 TCP**: TCP 는 패킷 하나가 늦으면 뒤 패킷도 함께 기다린다(head-of-line blocking). 좌표는 최신 값만 의미가 있으므로 UDP 로 보내고, 끊긴 동안에는 직전 속도로 이어 간다. UDP 가 막힌 망을 위해 TCP 대체 경로는 유지했다.
5. **서 있으면 보내지 않는다**: 움직일 때만 10Hz 로 보내고, 생존 신호는 3초 간격으로 분리했다.
6. **호스트가 받은 좌표를 자기 타이머로 다시 샘플링하던 문제**: 샘플이 빠지거나 중복되어 대시가 끊겼다. 받는 즉시 중계하도록 수정.
7. **잠자기 복귀 후 끊김**: SpriteKit 렌더 루프에 상태 갱신(tick)을 묶어 두니, 화면이 꺼지면 tick 도 멈췄다. 예비 타이머 → 디스플레이 링크 → tick 을 렌더링에서 분리하는 순서로 근본 원인에 접근했다. 네트워크와 생존 판정은 화면이 꺼져도 동작해야 하므로 `.common` 런루프 모드 타이머로 분리했다.

## 5. 연결 안정성 — 사무실 노트북의 현실

사용자 제보 → 재현 → 계측 → 수정의 순서로 처리한 문제들.

| 증상 | 원인 | 수정 |
|---|---|---|
| 잠금·절전 뒤 캐릭터가 전부 사라지고 앱을 재시작해야 복구됨 | 시계 두 개를 섞어 씀. SpriteKit 이 넘기는 시각이 잠금 해제 후 `systemUptime` 보다 238.5초 앞서, 경과 시간이 음수가 되어 tick 이 통째로 멈춤. 그 사이 보조 모니터가 붙으며 새로 만든 씬이 빈 채로 남음 | 시계를 `systemUptime` 하나로 통일. 계측으로 복구 시각을 15:53:42 로 예측했고 실제 15:53:43 에 복구되는 것으로 원인 확정 |
| Wi-Fi 를 옮기고 돌아오면 남아 있던 사람에게 내가 안 보임 | 인터페이스 이름이 같으면 네트워크 변경을 감지하지 못함 | 경로 상태·인터페이스·게이트웨이를 묶은 키로 변경 감지 |
| 나갔다 들어오면 내 캐릭터가 둘로 보임 | 같은 피어가 두 경로로 연결 | 남은 연결이 있으면 지우지 않고, 재입장 시 이전 것 교체 |
| 참가자 3명인데 나만 보임 | 끊긴 피어가 명단에 남음 | 좌표가 15초 끊긴 피어 제거, 0.25초마다 확인 |
| 밤새 잠자기 후 아침에 앱 종료 | 크래시 리포트 두 건이 같은 스택(`SKDisplayLinkControlQueue` 에서 SIGSEGV). 깨어나며 외장 모니터가 잠깐 사라지는 순간, SpriteKit 이 display link 를 정리하는 중에 앱이 같은 `SKView` 를 해제 | 화면 구성이 같으면 오버레이를 다시 만들지 않아 경쟁 자체를 제거 |
| 모달 대화상자를 15초 이상 열면 동료 화면에서 내가 사라짐 | `Timer` 가 `.default` 모드에만 등록되어 모달 중 정지 | `.common` 모드로 등록 |

**잠자기 상태 표시에 대한 판단**: "잠든 사람은 묘비로 표시하자"는 아이디어를 검토했지만, 받는 쪽에서는 "잠들었다"와 "네트워크가 끊겼다"를 구분할 수 없다는 점을 확인하고 연결 단위 판정은 그대로 두었다. 대신 묘비는 게임 요소(낙하사)로 활용했다.

## 6. 신뢰 경계 — LAN 에서 받은 데이터는 믿지 않는다

비판적 리뷰 에이전트 두 개(렌더링·입력 계층 / 네트워크·상태 계층)를 병렬로 실행해 찾은 문제들을 근거로 정리했다.

- **사칭**: hello 메시지의 id 를 검증하지 않아, LAN 의 누구든 Bonjour TXT 레코드에서 동료 id 를 읽고 그 사람 행세를 할 수 있었다 → 메시지에 id 를 포함하지 않고, **발신자는 연결에서 판정**한다.
- **메모리 무한 증가**: 16KB 메시지 상한이 개행을 찾은 뒤에만 검사되어 개행 없는 입력에 무력했다 → 버퍼·연결 수(32)·초당 줄 수(연결당 60, 전체 2,000)·대기 줄 수에 모두 상한 적용.
- **좀비 연결**: `.waiting` 상태를 처리하지 않아 닫힌 포트로 연결하면 영구히 남았다 → 핸드셰이크 5초 제한.
- **수신값 정규화**: 이름 20자, 채팅 50자, 좌표 범위, NaN 거부, 알 수 없는 캐릭터 번호 처리.
- **업데이트 URL**: GitHub 응답의 `html_url` 은 https + github.com 인지 확인한 뒤에만 연다.
- **App Sandbox 유지**: 앱 안에서 바로 업데이트하려고 샌드박스를 해제했다가, "LAN 에서 받은 데이터를 파싱하는 앱이라 샌드박스가 가장 값어치 있는 방어"라는 점을 확인하고 다시 활성화했다. 편의 기능보다 보안을 택한 결정.

- OpenSSL 3 기본 암호화로 만든 PKCS12 를 macOS Security 프레임워크가 읽지 못함 → 레거시 알고리즘으로 생성.

## 8. 성능 — 추측하지 않고 측정한다

- **CPU 원인 오판 사례**: 처음에는 "전체 화면 투명 오버레이 면적"이 원인이라고 판단했지만, 오버레이를 240pt 로 줄여도 8.7% → 8.2% 에 그쳤다. 실제 원인은 **매 프레임 `NSWindow.setFrameOrigin`** 으로 드래그 핸들 창을 옮기는 것이었고, 12Hz 로 제한하니 5.4% 가 되었다. 이 경험 이후 "구현 전에 실측으로 진단을 확인한다"를 작업 원칙으로 삼았다.
- **프레임 레이트**: 60fps → 30fps. 픽셀 게임에서 30fps 로 충분한지 직접 비교해 확인.
- **썸네일 캐시**: 캐릭터 선택 시 하이라이트가 한 박자 늦게 표시됨 → `SKTexture.cgImage()` 가 호출마다 GPU 에서 읽어 오는 비용(목록 재그리기 1회 192ms). 캐시 후 7.8µs. 같은 패턴이 앱 다른 곳에 있는지 이어서 점검.
- **두 시계 문제**: 별도 `Timer` 와 SpriteKit 렌더 루프가 서로 맞물리지 않아 떨림 발생 → 갱신을 렌더 루프 한 곳으로 통일.
- **좌표 전송이 절반 주기로 나가던 문제**: 0.1초 타이머 + 0.1초 간격 검사가 겹쳐 타이머 오차만큼 한 번씩 건너뛰었다. 측정해 보니 중앙값 0.199초. 중복 검사를 제거.

## 9. 조작과 게임 감각

- **자율 이동 → 직접 조종**: 처음에는 대기·걷기·뛰기 상태 기계와 전이 확률(예: 걷기 후 걷기 70 / 뛰기 15 / 대기 15, 진행 방향 유지 80%)로 NPC 처럼 돌아다니게 했다. 써 보니 "내 캐릭터"라는 느낌이 약해 자율 이동을 전부 제거하고 `⌥D` 조종 모드(←→ 이동, 두 번 누르면 대시, ↑ 점프·2단 점프, ↓ 인사·웅크려 걷기)로 바꿨다.
- **물리**: 낮은 fps 에서 오일러 적분이 꼭대기 높이를 절반으로 만드는 문제를 정확한 등가속도 식(`y += v·dt − ½g·dt²`)으로 해결. 낙하 피격은 마지막 프레임의 속도가 아니라 **최고 높이에서 구한 충격 속도 √(2gh)** 로 판정해 같은 높이에서 떨어지면 항상 같은 결과가 나오게 했다. 피격 기준 높이는 점프 높이에서 유도한다.
- **집어 들기**: 들어 올리는 순간 진행 중이던 모든 운동을 초기화하고, 얼굴 방향은 들어 올린 시점의 방향으로 유지한다. 들고 다닌 높이로 낙하 충격을 계산하지 않는다.
- **충돌**: 걷는 캐릭터끼리는 통과하고, **달릴 때만** 정면 충돌로 판정한다. 부딪히면 양쪽이 서로 반대로 튕겨 나가며 아파한다(서 있는 쪽도 포함).
- **묘비**: 아주 높은 곳에서 떨어뜨리면 아파하는 모션 → 비석이 솟아오름 → 조종 모드에서 ↑ 를 눌러야 바닥에서 튀어 오르며 살아난다.
- **점프 그림**: 루프 애니메이션 대신 수직 속도에 따라 도약·꼭대기·낙하 장면을 선택해 동작과 그림을 일치시켰다.
- **픽셀 정합성**: nearest 필터링, 정수 배율, 표시 위치를 2pt 격자에 스냅. 걷기 속도도 픽셀 격자에 맞춰 덜컥거림을 없앴다. 웅크려 걷기의 속도·프레임 비율(40pt/s ÷ 7fps = 5.71pt/장)을 걷기(70 ÷ 12 = 5.83)와 맞춰 발이 미끄러지지 않게 했다.
- **그림자**: 프레임 폭이 아니라 측정한 몸통 폭으로 크기를 정하고, 높이에 따라 네 단계로 줄인다.

## 10. 캐릭터 아트 파이프라인

- **라이선스 먼저 확인**: itch.io 에셋의 라이선스(CC BY 4.0)를 확인하고 출처를 README 와 `characters.txt` 에 표기. 원작자의 전체 시트 이미지는 저장소에 올리지 않았다 — "사용하는 것"과 "재배포하는 것"은 다르다.
- **색 슬라이더 제거 → 프리셋**: HSB 슬라이더는 조합하면 기괴한 색이 나온다. 큐레이션한 프리셋만 제공하기로 결정.
- **프리셋 규칙을 데이터로 찾음**: 처음 만든 8색 세트가 "컨셉이 없다"는 평가를 받았다. 원인을 분석하니 인접한 색상(hue)끼리 짝지었기 때문이었고, 명도 분포 지표로는 좋은 것과 나쁜 것을 구분하지 못했지만 **색상 거리**로는 구분되었다. 이후 "색상이 멀거나 한쪽이 무채색", "눈은 머리와 대비", "그라데이션 대신 밴딩" 같은 규칙을 검사기로 만들었다.
- **모든 모양에 같은 대우**: 어떤 캐릭터에는 흰색이 있고 어떤 캐릭터에는 없는 상태를 없애고, 모양마다 같은 수의 프리셋을 둔다. 원본 그림은 그대로 보존.
- **텍스트 도트 지도**: 모든 스프라이트를 24×24 텍스트 격자로 변환한 `characters.txt` 를 만들고, PNG 720장과 픽셀 단위로 일치하는지 왕복 검증. 이것을 기반으로 고양이·사람·유령 등을 새로 그렸다.
- **이미지 생성 AI 활용**: 144×144 격자 이미지와 행별 동작 설명만 주는 프롬프트(`image_prompt.txt`)를 설계. AI 가 격자를 이탈하는 문제를 겪으며 "색 지정·레퍼런스·세부 지시를 넣지 않고 격자 규칙만 강조"하는 쪽으로 다듬었다. 생성된 이미지는 큰 블록 기준으로 칸별 최빈색을 채워 24px 로 변환.
- **편집 도구**: 스프라이트 시트를 한 장씩 칠하고 도트 지도를 바로 확인하는 가벼운 HTML 편집 페이지를 만들어 직접 수정.
- **다양성**: 사람 캐릭터에 피부색 세 가지를 추가.

## 11. UX 원칙

- **Spotlight 같은 채팅**: `⌥F` 로 화면 아래 가운데에 입력줄이 뜨고, 열리자마자 포커스를 잡고, 다른 곳을 클릭하면 사라지고, 닫으면 **원래 앱으로 포커스를 되돌린다**. macOS 14 부터 `activate()` 가 무시되어 `yieldActivation(to:)` 를 먼저 호출해야 한다는 것을 파일 로그로 찾아냈다.
- **단축키 선정**: `⌥Space` 는 Alfred 등 다른 앱의 기본값과 충돌. 타이핑하다가 손을 홈 row 에서 떼지 않고 누를 수 있는 `⌥F`(채팅), `⌥D`(조종)로 결정. Carbon `RegisterEventHotKey` 를 써서 샌드박스에서도 손쉬운 사용 권한 없이 동작한다.
- **입력 중 표시**: 처음에는 "더 어렵다"며 보류했다가, 이후 iMessage 방식의 `…` 말풍선을 가장 단순한 구현으로 추가. 더 단순한 버전과 비교해 더 안전한 쪽을 선택.
- **디바운스 대신 적용 버튼**: 캐릭터를 바꿀 때마다 즉시 전송하던 것을 "적용" 버튼으로 바꾸고 연타만 막았다. 디바운스 코드가 통째로 사라졌다.
- **문구를 덧붙이지 않는다**: 동작을 고칠 때 안내 문구를 끼워 넣지 않는다. "설치가 끝나고 다시 실행됩니다" 같은 문구도 군더더기로 판단해 제거.
- **README 는 마케팅 문서**: "이 README 를 읽고 사람들이 써 보고 싶다고 생각해야 한다." 기능 나열 대신 사용 장면과 걱정거리 해소(일을 방해하지 않음, 가입 없음, 대화가 남지 않음) 중심으로 다시 썼다. 프리셋 개수처럼 자주 바뀌는 숫자는 적지 않는다.
- **이름**: Offiky = **Offi**ce + Luc**ky**. 사무실에 사는 행운의 마스코트.

## 12. 일하는 방식

- **코드 읽기로 낸 진단은 실측으로 확인한 뒤 고친다.** 파일 로그, 같은 맥에서 앱 두 개 실행, 별도 Swift 프로그램으로 API 동작 증명, 프레임 단위 추적. CPU·패킷 간격·렌더 지연 모두 측정값으로 결정했다.
- **재현 테스트가 우연히 통과하지 않는지 확인한다.** 두 경로가 같은 결과를 내는 위치를 골라 테스트가 거짓 통과한 사례가 있어, 결과가 갈리는 입력을 골라 다시 작성했다. 정의상 항상 참인 단언도 찾아 제거.
- **단순함 우선.** "코드는 간단할수록 좋다." 호스트 구조가 남긴 설정값, 한 번만 호출하는 헬퍼, 전달만 하는 코드를 주기적으로 정리했다. 기능이 덜 필요하면 기능 자체를 제거(캐릭터 숨기기, 미니맵, 벽, 착지 먼지).
- **비판적 리뷰를 병렬로.** 계층별 리뷰 에이전트를 나눠 실행하고, 오탐이라고 판단한 지적은 수정하지 않았다.
- **시험 인스턴스 분리.** 디버그 빌드는 번들 id 를 바꾼 복사본으로 실행하고, 테스트용 채널을 따로 지정해 실제 동료들에게 시험 캐릭터가 보이지 않게 했다. 테스트가 실제 방 설정을 지우던 문제도 이 원칙으로 막았다.
- **디버그 빌드 구분.** 디버그 앱은 메뉴바 아이콘을 망치로, 버전 뒤에 "· 디버그"를 표시해 배포본과 혼동하지 않게 했다.

## 14. 자기소개용 요약

> 같은 사무실 Wi-Fi 에 있는 동료들의 픽셀 캐릭터가 화면 아래를 걸어 다니는 macOS 메뉴바 앱을 혼자 4주 동안 만들어 58번 배포했습니다. 서버 없이 Bonjour 로 서로를 찾고 P2P 로 위치를 동기화합니다. 핵심 과제는 잠자기와 Wi-Fi 이동이 잦은 사무실 노트북 환경에서 상대 캐릭터가 끊기지 않게 하는 것이었고, 네트워크 구조를 측정값에 근거해 다섯 번 바꿨습니다.

**2분 버전에 넣을 것**
1. 문제: 서버 없음 · 모니터 구성이 제각각 · 노트북이 자주 잠들고 이동함
2. 가장 어려웠던 것: 토폴로지 선택 (호스트 중계 vs 풀 메시, Wi-Fi airtime 기준으로 방당 15명 상한)
3. 끊김 해결: 보간 + 실측 기반 렌더 지연 + 좌표만 UDP
4. 일하는 방식: 진단은 계측으로 확인한 뒤 수정 (CPU 원인 오판 사례)

## 15. 핵심 개념 정리

### 15-1. TCP vs UDP, Head-of-Line blocking

- **TCP**: 순서와 도착을 보장한다. 패킷 하나가 유실되면 재전송될 때까지 **뒤에 도착한 패킷도 애플리케이션에 전달되지 않는다** (HOL blocking).
- **UDP**: 보장이 없다. 대신 도착한 것은 바로 전달된다.
- **이 프로젝트**: 좌표는 "최신 값만 의미 있는 데이터"라 늦게 온 옛 좌표는 쓸모없다 → UDP. 채팅·입장·프로필은 유실되면 안 된다 → TCP. UDP 가 막힌 망을 위해 좌표도 TCP 로 보내는 대체 경로를 남겼다.
- **꼬리질문 대비**: "TCP 와 UDP 를 같이 쓰면 서로 방해하지 않나?" → 같은 링크 대역을 나눠 쓰지만, 채팅은 트래픽이 아주 작아 좌표 전송을 지연시킬 정도가 아니다. HOL blocking 은 **한 TCP 연결 안에서** 생기는 문제라 별도 UDP 흐름에는 영향이 없다.

### 15-2. 엔티티 보간(Entity Interpolation)과 렌더 지연

- 받은 좌표를 바로 그리면 패킷 간격의 흔들림(jitter)이 그대로 움직임의 흔들림이 된다.
- **방법**: 현재 시각보다 `delay` 만큼 과거 시점을 그린다. 그 시점을 감싸는 두 샘플 사이를 선형 보간한다. 다음 샘플이 이미 도착해 있으므로 부드럽다.
- **대가**: 상대 캐릭터는 항상 `delay` 만큼 늦게 보인다. 이 앱은 경쟁 게임이 아니라서 지연보다 부드러움이 중요하다.
- **값 결정**: Wi-Fi 에서 도착 간격 실측 → 중앙값 0.1초, 최대 0.21초(가끔 0.4초). 0.2초 지연이면 1~5% 프레임에서 다음 샘플이 없었고, 0.3초에서 0%. 이후 도착 간격에 맞춰 **0.15~0.5초 사이에서 자동 조정**.
- **외삽(Dead Reckoning)**: 다음 샘플이 없을 때 직전 속도로 추측해 그리는 것. 틀리면 되돌아가는 "고무줄" 현상이 생긴다. 이 앱은 **최대 0.5초만** 외삽해 손실 몇 건만 가린다.
- **보낸 시각 포함**: 받은 시각으로 보간하면 망 지연 변화가 그대로 반영된다. 송신 시각을 함께 보내 고르게 재생한다.

### 15-3. 네트워크 토폴로지와 Wi-Fi airtime

| 구조 | 연결 수 | 초당 송신 패킷 (n명, f Hz) | 장점 | 단점 |
|---|---|---|---|---|
| 호스트 중계(star) | n−1 | 클라이언트 n·f + 호스트 재전송 | 송신자가 사실상 호스트 하나 | 호스트가 떠나면 교체 동안 끊김, 호스트 부하 |
| 풀 메시 | n(n−1)/2 | n(n−1)·f | 호스트 없음, 한 사람이 떠나도 나머지는 영향 없음 | 인원 제곱에 비례 |
| UDP 멀티캐스트 | 0 (그룹) | n·f | 패킷 수 최소 | AP 가 막거나 느린 속도로 전송, ACK 없음 |

- **숫자로 말하기**: 50명 · 10Hz 풀 메시 = 50 × 49 × 10 = **24,500 패킷/초**. 15명이면 15 × 14 × 10 = **2,100 패킷/초**.
- **Wi-Fi 에서 패킷 수가 문제인 이유**: Wi-Fi 는 모든 기기가 한 채널을 나눠 쓰는 반이중 매체다. 패킷마다 채널 경쟁(CSMA/CA), 프레임 헤더, ACK, 프레임 간 대기 시간이 붙는다. 50바이트짜리 작은 패킷이면 실제 데이터보다 이 고정 비용이 훨씬 크다. 그래서 **바이트 수가 아니라 패킷 수와 송신자 수**가 체감 성능을 정한다.
- **멀티캐스트를 쓰지 않은 이유**: 많은 AP 가 멀티캐스트를 가장 낮은 기본 속도로 보내 airtime 을 오히려 많이 쓰고, 기업망은 멀티캐스트를 제한하는 경우가 많다. 재전송도 없다.
- **최종 선택**: 채널 1~20, 채널당 15명, 채널 안 풀 메시. 인원 상한을 채널 단위로 두면 **전체 사용자 수와 무관하게 한 사람의 부하가 고정**된다 (200명이 10명씩 나뉘어도 한 사람당 연결 9개).

### 15-4. 서비스 발견: Bonjour / mDNS

- 서버 없이 `_offiky._tcp` 서비스를 광고하고 탐색한다. DNS 질의를 멀티캐스트(224.0.0.251:5353)로 보낸다.
- **링크 로컬 범위**라 라우터를 넘지 못한다 → 같은 서브넷에서만 발견된다. **VPN 으로 원격 접속한 사람은 보이지 않는다.** 이것이 "서버 없음"의 대가다.
- TXT 레코드는 누구나 읽을 수 있다 → 여기에 넣은 id 는 공개 정보로 취급해야 한다 (사칭 문제로 이어짐, 15-8).

### 15-5. 분산 시스템 기본: 선출, split-brain, 중복 연결

- **결정적(deterministic) 선출**: 투표 메시지 없이 "모두가 같은 정보로 같은 규칙을 적용하면 같은 답"을 얻는다 (예: id 가 가장 작은 사람).
- **split-brain**: 두 노드가 서로 자신을 호스트로 판단하는 상태. 이 프로젝트에서는 실패한 피어를 10초 동안 후보에서 제외했는데, 제외가 끝나도 재선출이 실행되지 않아 두 사람이 모두 호스트로 남았다. **상태가 만료되는 시점에 재평가를 예약**해 해결.
- **선출 규칙의 UX**: "id 가 가장 작은 사람"은 다시 들어온 사람이 호스트를 빼앗아 교체가 불필요하게 일어난다 → "먼저 들어온 사람이 유지"로 변경.
- **중복 연결**: 풀 메시에서 A 와 B 가 동시에 서로를 발견하면 연결이 두 개 생긴다 → id 가 작은 쪽만 연결을 연다.
- **합의 없는 정원 판정**: 각 기기가 자기 명단으로 판정하면 동시 입장 시 기기마다 결과가 다르다. 완전한 해결은 합의 알고리즘이지만, 비용 대비 "아직 아무와도 연결되지 않은 경우에만 나간다"로 범위를 좁혔다 (약점 항목 참고).

### 15-6. 동시성과 비동기 콜백

- **경쟁 상태**: main 스레드와 네트워크 큐가 같은 Dictionary 를 잠금 없이 수정하면 EXC_BAD_ACCESS 가 날 수 있다 → 네트워크 상태는 한 직렬 큐에서만 접근한다.
- **취소 후 콜백**: `NWConnection.cancel()` 뒤에도 마지막 수신 콜백이 한 번 온다. 별도 Swift 프로그램으로 증명했다. 이 콜백이 "연결 실패"로 처리되어 **새 호스트**를 제외하던 버그 → 콜백 안에서 "지금 관리 중인 그 연결 객체인가"를 객체 동일성(`===`)으로 확인.
- **교훈**: API 문서에 없는 동작은 추측하지 말고 최소 재현 프로그램으로 확인한다.

### 15-7. 시간과 런루프

- **단조 시계**: 경과 시간은 벽시계가 아니라 `systemUptime` 같은 단조 증가 시계로 잰다.
- **시계 두 개를 섞은 버그**: SpriteKit 이 넘기는 시각과 `systemUptime` 을 섞어 썼다. 잠금 해제 후 둘이 238.5초 어긋나 경과 시간이 음수가 되었고 tick 이 멈췄다. 계측으로 복구 시각을 15:53:42 로 예측했고 실제 15:53:43 에 복구되어 원인을 확정했다.
- **런루프 모드**: `Timer.scheduledTimer` 는 `.default` 모드에만 등록된다. 모달 대화상자는 다른 모드로 런루프를 실행하므로 타이머가 멈춘다 → 15초 넘게 대화상자를 열면 좌표가 끊겨 동료 화면에서 내가 사라졌다. `.common` 모드로 등록해 해결.
- **렌더 루프와 로직 분리**: 화면이 꺼지면 렌더 루프도 멈춘다. 네트워크와 생존 판정은 화면과 무관하게 동작해야 하므로 분리했다.

### 15-8. 신뢰 경계와 입력 검증

- **원칙**: LAN 에서 받은 바이트는 외부 입력이다. 같은 사무실이라도 믿지 않는다.
- **사칭**: 메시지 안의 id 를 믿으면 TXT 레코드에서 읽은 남의 id 로 행세할 수 있다 → **발신자는 메시지가 아니라 연결로 판정**한다.
- **자원 고갈**: 메시지 크기 검사가 개행을 찾은 뒤에만 실행되어, 개행 없는 입력을 보내면 버퍼가 무한히 커졌다 → 버퍼·연결 수·초당 줄 수·대기 줄 수에 모두 상한.
- **좀비 연결**: `.waiting` 상태를 처리하지 않아 연결이 영구히 남음 → 핸드셰이크 5초 제한.
- **값 정규화**: 이름·채팅 길이, 좌표 범위, NaN 거부, 모르는 캐릭터 번호.

### 15-9. macOS 배포: 코드 서명, 공증, Gatekeeper, 샌드박스

- **코드 서명**: 앱이 서명 이후 변조되지 않았음을 보장한다. 자체 서명 인증서로도 서명은 되지만 Apple 이 신뢰하는 인증서는 아니다.
- **Developer ID + 공증(notarization)**: Apple 이 앱을 자동 검사하고 승인 기록을 남긴다. Gatekeeper 가 경고 없이 실행을 허용한다. 연 $99.
- **Gatekeeper 와 quarantine**: 인터넷에서 받은 파일에는 `com.apple.quarantine` 확장 속성이 붙는다. 공증되지 않은 앱은 이 속성 때문에 실행이 막힌다. Homebrew cask 가 설치 후 이 속성을 제거해 사용자의 수동 단계를 없앴다.
- **Hardened Runtime**: 코드 주입·디버거 연결 등을 막는 런타임 보호. 공증의 필수 조건이다.
- **App Sandbox**: 앱이 접근할 수 있는 파일·네트워크·기기를 entitlements 로 제한한다. 샌드박스 앱은 `/Applications` 의 자기 자신을 교체할 수 없어 앱 안 자동 업데이트가 어렵다 (Sparkle 은 XPC 서비스로 우회).
- **TCC 로컬 네트워크 권한**: macOS 가 LAN 접근 시 사용자에게 묻는 권한. 터미널에서 실행한 프로세스는 터미널의 권한을 이어받아 실제 사용자 경로를 시험하지 못한다는 함정이 있었다.
- **유니버설 바이너리**: `-destination 'platform=macOS'` 는 빌드 머신 아키텍처만 빌드한다. Intel 맥에서 실행되지 않는 배포본이 나갔고, `generic/platform=macOS` 와 `lipo -archs` 검사를 릴리스 스크립트에 추가했다.

### 15-10. 렌더링 성능

- **측정이 추측을 이긴 사례**: "투명 오버레이 면적"이 원인이라 판단 → 면적을 줄여도 8.7% → 8.2%. 실제 원인은 매 프레임 `NSWindow.setFrameOrigin`. 12Hz 로 제한해 5.4%.
- **숨은 GPU 왕복**: `SKTexture.cgImage()` 는 호출마다 GPU 에서 읽어 온다. 목록 재그리기 1회 192ms → 캐시 후 7.8µs.
- **물리 적분**: 오일러 적분 `y += v·dt` 는 큰 dt 에서 오차가 커 점프 꼭대기가 절반이 됐다. 등가속도는 해석해(`y += v·dt − ½g·dt²`)가 있으므로 정확한 식을 쓴다.
- **판정은 상태에서 유도**: 낙하 피격을 마지막 프레임 속도로 판정하면 fps 에 따라 결과가 달라진다(같은 600pt 낙하에서 94 vs 1150). 최고 높이 h 에서 `√(2gh)` 로 구해 항상 같은 결과.

### 15-11. SwiftUI 상태 관찰

- `MenuBarExtra` 메뉴는 **관찰 중인 상태가 바뀔 때만** 다시 그린다. 관찰 대상이 아닌 싱글턴 값을 읽으면 실행 시점 값에 고정된다 → 참가자 수가 1에 멈춘 버그, 버전 불일치 경고가 뜨지 않던 버그. `@Observable` 객체로 옮겨 해결.

## 16. 예상 질문과 답

**Q. 왜 서버를 두지 않았나요?**
가입·설정 없이 같은 Wi-Fi 에 있으면 바로 보이는 것이 제품의 핵심이었습니다. 서버를 두면 계정, 운영 비용, 대화가 외부로 나가는 문제가 생깁니다. 대가로 VPN 원격 접속자는 볼 수 없고, 50명 이상 대규모 동시 접속은 서버가 더 낫다는 점은 인정하고 채널당 15명 상한으로 범위를 정했습니다.

**Q. 왜 호스트 방식에서 풀 메시로 바꿨나요? 풀 메시는 확장성이 나쁘지 않나요?**
맞습니다. 50명이면 초당 24,500 패킷이라 호스트 방식이 airtime 측면에서 유리합니다. 실제로 한때 그 이유로 호스트 방식으로 돌아갔습니다. 그런데 사무실 노트북은 잠자기·이동이 잦아 호스트가 너무 자주 바뀌었고, 교체할 때마다 모두의 화면이 끊겼습니다. 그래서 인원을 채널당 15명으로 제한해 패킷 수를 2,100/초로 묶고, 한 사람이 떠나도 나머지에 영향이 없는 풀 메시를 택했습니다.

→ 꼬리: "15명은 어떻게 정했나요?" 인원 제곱에 비례하는 패킷 수를 기준으로, 사무실 Wi-Fi 에 부담을 주지 않는 수준과 한 팀 규모를 함께 고려했습니다. 실측으로 정한 값은 아니라는 점은 약점입니다.

**Q. 상대 캐릭터가 끊겨 보이는 문제를 어떻게 해결했나요?**
세 단계입니다. 첫째, 받은 좌표를 바로 그리지 않고 과거 시점을 보간해 그립니다. 둘째, 지연값을 Wi-Fi 도착 간격 실측(중앙값 0.1초, 최대 0.21초)으로 정했고 이후 자동 조정으로 바꿨습니다. 셋째, 좌표만 UDP 로 보내 TCP 의 HOL blocking 을 피했습니다.

**Q. 가장 어려웠던 버그는?**
잠금 해제 뒤 캐릭터가 전부 사라지고 재시작해야만 복구되던 버그입니다. 시계 두 개를 섞어 써서 238.5초 어긋났고, 경과 시간이 음수가 되어 tick 이 멈췄습니다. 사용자가 "주 모니터가 먼저 켜졌을 때는 보였다가 보조 모니터가 붙자 사라졌다"고 준 관찰과 계측 로그를 맞춰 보고, 복구 시각을 1초 오차로 예측해 원인을 확정했습니다.

**Q. 보안은 어떻게 고려했나요?**
LAN 입력을 외부 입력으로 취급했습니다. 발신자를 메시지가 아니라 연결로 판정해 사칭을 막고, 버퍼·연결 수·전송 빈도에 상한을 두고, 수신값을 정규화했습니다. 앱 안 자동 업데이트를 위해 샌드박스를 해제했다가, 파싱하는 앱에서 샌드박스가 가장 값어치 있는 방어라 판단해 되돌렸습니다. 다만 통신은 암호화하지 않은 평문입니다 (약점).

**Q. Developer ID 없이 어떻게 배포했나요?**
자체 서명 인증서로 서명하고 Homebrew cask 로 배포했습니다. 공증이 없어 Gatekeeper 가 막는데, cask 가 설치 후 quarantine 속성을 제거하게 했습니다. 업데이트는 GitHub 릴리스를 확인해 메뉴바에 빨간 점을 표시하고, 버튼 하나로 터미널에서 `brew upgrade` 를 실행합니다. Sparkle 도 검토했지만 Homebrew 와 이중으로 버전을 관리하게 되어 채택하지 않았습니다.

**Q. 테스트는 어떻게 했나요?**
좌표 변환, 화면 구성 변경, 물리, 프로토콜 정규화 등 단위 테스트 147개를 Swift Testing 으로 작성했습니다. 네트워크는 같은 맥에서 번들 id 를 바꾼 앱 두 개를 별도 채널로 실행하고, 지연·손실을 모사하는 디버그 옵션으로 확인했습니다. 리뷰에서 "정의상 항상 참인 단언"이나 "두 경로가 같은 결과를 내서 우연히 통과하는 테스트"를 찾아 고친 경험도 있습니다.

**Q. AI 도구를 어떻게 활용했나요?**
구현과 리뷰에 활용했고, 계층별로 비판적 리뷰 에이전트를 나눠 실행했습니다. 대신 AI 가 코드만 읽고 낸 진단은 그대로 믿지 않고 재현·계측으로 확인한 뒤 수정했습니다. CPU 원인 오판이 그 원칙을 세운 계기입니다. 리뷰 지적 중 오탐으로 판단한 것은 수정하지 않았습니다.

**Q. 다시 만든다면 무엇을 다르게 하겠나요?**
17장 약점 항목에서 고른다. 추천: 토폴로지를 바꾸기 전에 airtime 실측 환경부터 만들기, 시계를 처음부터 하나로 정하기.

## 17. 약점과 한계 (먼저 말할 수 있게)

- **통신이 평문이다.** 같은 LAN 의 누구나 채팅과 좌표를 볼 수 있다. 대화를 저장하지 않는 것과 엿볼 수 없는 것은 다르다. 개선: 채널별 키로 TLS 또는 메시지 암호화.
- **정원 판정에 합의가 없다.** 동시 입장 시 기기마다 판정이 다를 수 있다. 범위를 좁혀 피해를 줄였을 뿐 근본 해결은 아니다.
- **15명 상한은 실측값이 아니다.** 패킷 수 계산과 판단으로 정했다. 실제 사무실 AP 에서 인원별 airtime 을 측정하지 못했다.
- **여러 맥에서 Wi-Fi 를 실제로 끊는 시험은 자동화하지 못했다.** 단위 테스트와 같은 맥의 두 인스턴스, 망 모사로 대체했다.
- **토폴로지를 여러 번 왕복했다.** 요구사항(노트북 이동 빈도)을 초기에 측정했다면 바꾸는 횟수를 줄일 수 있었다. 이 경험을 "제약을 먼저 측정한다"는 교훈으로 말한다.
- **Apple 신뢰 체계 밖 배포.** 자체 서명이라 사용자는 Homebrew 를 신뢰하는 셈이다. 공개 배포를 넓히려면 Developer ID 와 공증이 필요하다.
- **같은 서브넷에서만 동작한다.** 재택·VPN 사용자를 포함하려면 서버(또는 릴레이)가 필요하다.

### 원칙으로 지킨 판단

- **$99 를 내지 않는다**: "나중에 99달러를 안 낼 수도 있다." → 개인 Developer ID 에 묶지 않고 자체 서명.
- **샌드박스를 지킨다**: 샌드박스를 해제했다는 보고에 "우리는 뭘 포기한 건데?"라고 되묻고, 답을 들은 뒤 다시 활성화하고 업데이트는 명령 복사로 결정.
- **색은 내가 고른 것만**: "색 조절이 있으면 사실상 기괴한 색이 된다." → 슬라이더 제거, 프리셋 제공.
- **모든 캐릭터에 동등한 색**: "어떤 캐릭은 흰색이 있고 어떤 캐릭은 없다. 동등해야 한다."
- **남의 그림은 재배포하지 않는다**: "내 것도 아닌데 사용하는 것만으로 족하다." → 원작 전체 시트를 저장소에서 제거.
- **README 는 고객이 읽는 문서**: "읽고 써 보고 싶어져야 한다."
- **코드는 단순할수록 좋다**: 기능이 늘 때마다 군더더기 점검을 요청하고, 필요 없어진 기능(벽, 미니맵, 캐릭터 숨기기 등)은 제거.
- **시작 위치는 예측 가능해야 한다**: 무작위 대신 주 화면 가운데.

## 20. AI 와 협업하며 생긴 일

### 내가 AI 를 바로잡은 것

| 상황 | AI 의 판단 | 내가 바로잡은 내용 |
|---|---|---|
| 첫 실행 | 투명 픽셀은 클릭이 통과한다고 가정 | 실행해 보니 빨간 상자가 모든 클릭을 가져감 → 오버레이에서 마우스 이벤트 무시 + 별도 드래그 창 |
| 스프라이트 방향 | 눈 위치를 분석해 왼쪽을 본다고 판단 | 실제로 보니 뒷걸음질 → 오른쪽 기준으로 수정 |
| 그림자 | 레퍼런스 모양에 맞춘다며 크기를 임의로 변경 | "아까가 더 낫다" → 되돌리고 좌우 1px 만 확장 |
| 앱 아이콘 | 여러 차례 새로 디자인 | "32×32 도화지에 절반은 개구리 16px, 나머지는 배경과 땅" 이라고 구체적인 규격을 제시 → 채택 |
| 색 프리셋 | 8색 세트 제작 | "컨셉이 전혀 없다" → 원인이 인접 색상 조합임을 분석하는 계기 |
| 작업 범위 | 디자인 변경 요청에 동작까지 변경 | "디자인만 바꾸라" → 표시 조건·타이밍은 디자인이 아니라는 원칙 정립 |
| 자동 실행 | 요청 없이 커밋·테스트·재실행 | "왜 자동화를 멋대로 하나" → 요청한 것만 실행 |
| 작업 규모 | 캐릭터 시안에 과도한 토큰 사용 | "가볍게 만들라는 것이었다" → 기본은 가볍게 |
| 화면 문구 | 동작 수정에 안내 문구 추가 | "설치가 끝나고 다시 실행됩니다 같은 건 군더더기" → 문구를 덧붙이지 않음 |

### AI 가 바로잡은 내 생각

| 내 생각 | 확인 결과 |
|---|---|
| 잠든 사람은 묘비로 표시하자 | 받는 쪽은 "잠듦"과 "네트워크 끊김"을 구분할 수 없다 → 묘비는 낙하사 게임 요소로 활용 |
| 호스트 방식은 네트워크 부하가 없다 | 호스트가 모든 패킷을 다시 보내므로 부하는 호스트에게 몰린다. 다만 무선 송신자 수가 줄어드는 장점은 맞다 |
| 원점을 옮기면 음수 좌표가 생긴다 | 띠 왼쪽 끝 원점에서는 음수가 없다 (확인 후 "내가 틀렸다"고 정리) |
| 샌드박스에서도 권한만 받으면 자동 업데이트가 된다 | 샌드박스 앱은 `/Applications` 의 자기 자신을 교체할 수 없다 |
| VPN 으로 접속해도 보일까 | mDNS 는 링크 로컬이라 라우터를 넘지 못한다 |

### 외부 조언을 검증한 것

다른 AI·자료에서 얻은 조언을 그대로 적용하지 않고 이 프로젝트 기준으로 검증했다. 면접에서 "정보를 어떻게 판단하나"에 대한 답으로 쓸 수 있다.

| 외부 조언 | 검증 후 판단 |
|---|---|
| 트래픽 절감 5가지 (정지 시 전송 중단, 이동 중 5~10Hz, 바이너리화, 같은 방만 전송, 채팅도 방 안에서만) | 맞지만 순서가 틀렸다. 바이너리화는 바이트만 줄이고 send 호출 수는 줄이지 않는다. id 축소(−32%)와 여러 틱 묶어 보내기(−65%, send 50배 감소)를 먼저 적용해 목표에 도달했고, 프레이밍을 새로 써야 하는 바이너리화는 하지 않았다 |
| 무선 20명이면 풀 메시보다 호스트 중계 | 패킷 수 측면에서는 맞음. 하지만 이 환경의 실제 문제는 호스트 교체 빈도라 결론이 다름 |
| 50명이면 자동 선출 호스트 + 즉시 이전 | 호스트 교체를 아무리 다듬어도 교체 자체를 없애는 것보다 낫지 않다고 판단 |
| Slither.io 처럼 좌표 대신 방향·속도 변경 이벤트 + 주기 보정 | 트래픽은 줄지만 보정 로직이 복잡해짐. "움직일 때만 전송"으로 충분 |
| 샌드박스에서도 Sparkle 2 로 자동 업데이트 가능 | 사실이지만 Homebrew 와 이중 버전 관리 문제. 시도해 봤으나 앱이 실행되지 않아 중단하고 Homebrew 유지 |
| UDP 멀티캐스트로 근본 개선 | 사무실 AP 의 멀티캐스트 제한과 실패 사례 때문에 기각 |
| StarCraft 는 P2P + lockstep 으로 트래픽이 적다 | 입력만 교환하는 결정적 시뮬레이션이라 위치를 공유하는 이 앱과 전제가 다름 |
| tick 대신 SKAction 을 썼어야 하지 않나 | 애니메이션에는 맞지만 네트워크 좌표 동기화는 update 에서 보간하는 쪽이 맞다. 다만 지적을 계기로 구조를 다시 점검 |
